## advice 的本地校正（实施时必须落实）

1. **§1/§8 基线**：远端调查 SHA 未知，不把后来查到的远端提交倒填成研究基线，也不批量改原文 branch links 冒充固定证据。本轮本地 HEAD 为 `817a73da60676e1631229eebdb867f070b4ed043`；开工再核对相关符号与工作树。§15.24 已在本地，保留本地新增内容。
2. **§2.2/§4 事务**：字段允许空值是必要条件，不是 reader-ready 分拆已获完整验证的证明。契约对齐必须说明 Material/Sentence/源资源/publication 的成功边界、导入失败与重试、文件和数据库之间的发布次序；准备 Sidecar 失败不能损坏已提交正文。实现不能只跳过 `_tokenize` 就当作解耦完成。
3. **§3.6 投影**：明确 HTML 隐藏语义、被丢弃的作者样式、块分隔符和图片占位对规范文本的处理；不可凭“隐藏文本排除”使用随布局变化的 computed style 或每节点 NFC。若改变现有 canonical text，明确版本与兼容范围，不静默改变旧 Sentence/anchor。DOM 重投影一致性须有测试。
4. **§3.6 版本**：一旦保存或缓存 publication/规范投影，就必须能核验源内容身份及生成版本；不能等批注阶段才发现当前程序无法解释旧投影。版本可用最小存储设计，未必新增专门表，但只有运行时常量而无法核验旧产物不够。禁止更新后用新算法默默重解释旧坐标。
5. **§3.5/§5 iframe**：沿用浏览器同源路径。当前 Vite 已代理 `/materials` 到后端，优先让 chapter 的相对 URL 走此代理；实际生产拓扑仍需核对，CORS 不解决 DOM 访问。只启用必要 sandbox 权限，响应 CSP 与资源 allowlist 一起验证；CSP 的 `'self'` 不能代替 publication 资源边界。
6. **§5 加载失败**：不要依赖 iframe `onError` 或只凭 `onLoad` 报成功。浏览器可能在失败时仍触发 load，且不触发 error；通过受控 API 的状态及同源文档的可信标识/校验结果识别正确章节，覆盖不存在、损坏、拒绝和超时的反馈。依据：[MDN iframe 事件行为](https://developer.mozilla.org/en-US/docs/Web/HTML/Reference/Elements/iframe#error_and_load_event_behavior)。
7. **§7 验收**：真实样本不足三个章节时按实际章节数验证首尾边界，多章合成样本补充顺序检查；不为机械满足“3 个 spine”排除有效样本。无目标书可先完成技术验证，但必须标记真实书体验待验证，不能宣布 RF-01 完整验收。

### Correctness blocker stabilization（2026-09-15）

- hidden void projection：`hidden` / `aria-hidden="true"` 的 HTML/SVG void 或自闭合元素现在原子忽略，不再开启等待结束标签的 skip scope；正文后续可见文本在 controlled XHTML 与 canonical projection 中保持一致。非 void 隐藏节点仍按原有范围丢弃。
- publication placeholder：编译阶段的章节重映射与 HTTP served HTML 的 placeholder 展开均只处理 `href` / `src` 属性值，普通正文中的 `__LJ_RESOURCE_*__`、`__LJ_DISABLED_LINK__`、`__LJ_CHAPTER_*__` 不再被全局替换；served body 重投影仍等于 manifest canonical text。
- percent-encoded URI：先对 raw href 做 `urlsplit`，仅对 `parsed.path` 解码一次；ZIP member 名称不再作 URI 解码，`%23` / `%3F` 可作为合法文件名字符，真实 fragment 仍单独保留。
- 本轮未递增 `EPUB_PROJECTION_VERSION`，继续使用 pre-release `learningj-epub-publication-v4`；hidden 规则会使受影响 EPUB 的 canonical text/offset 变化，开发库需显式重建并重新导入，不静默重解释旧 publication。其余非阻塞审查项（EPUB `external_reference` API 收紧、persisted manifest 深层 typed 校验、原始上传 capped read、模块拆分与前端 `MaterialWorkspace` 重构）留给后续切片。
