# LearningJ 测试与验收标准

状态：按用户 2026-09-13 的要求生效。规范测试选择与交付证据；不是代码、脚本或 CI 已完成分组的声明。

## 适用与优先级

后续新派发任务采用本标准：按变更影响和用户动作选择验证，不默认重复全仓全套。旧包的测试数量、前端/后端/demo 全套联跑不自动成为新任务门槛。仍明确按旧包验收时，派发者应写明采用本标准后的检查范围；未重派前不能把少跑检查报告为旧包完整通过。

本标准不改变数据字段、状态、定位、安全或用户数据保护契约。不以“减负”忽略当前功能实际依赖的 sidecar 一致性、事务、版本、备份恢复等要求。范围草案也不能授权绕过现行语义。

## 选择检查

| 变更 | 默认必要验证 | 不默认要求 |
|---|---|---|
| 文档 | diff、链接与文档状态/权威一致性 | 应用构建和测试 |
| 文案、样式 | 受影响页面实际视觉检查；相关静态检查 | 为颜色、类名、固定 DOM 层次新建测试；后端/demo 全套 |
| 前端行为 | 受影响交互测试；前端 lint、类型/构建；真实页面操作 | 未触及的后端全套和未来学习页面矩阵 |
| 后端行为 | 针对变更的单元/数据库/API 测试；项目已有的适用静态检查 | 无关前端/demo 构建；为流程完整性引入新检查工具 |
| API 或共享类型 | 生产方行为测试、生成产物与类型漂移检查、受影响消费方测试和构建 | 用多份手写 fixture 重复定义同一接口 |
| 纯重构/移动 | 简短重构计划；缺失时先补关键行为回归；导入/边界静态检查和受影响测试 | 仅为维持旧路径/文件数量而锁死组织结构 |
| 导入/定位/数据写入 | 目标行为加相关安全、重复操作、失败/重启恢复测试 | 以 UI 冒烟替代数据正确性证明 |

修复 bug 优先写能重现问题的回归；小范围可逆样式/文案不要求先写测试。对同一语义优先选最便宜且可靠的一层验证；跨边界风险才增加集成测试。

## 阅读器不可减掉的保护

- EPUB/Yomitan 归档的路径、体积、资源访问与主动内容边界；不覆盖源文件。
- 章节顺序、规范化、Unicode code-point 半开区间、选区唯一定位；布局变化与重新打开后能找回。
- 批注写入/编辑/删除与读回；失败不误报成功，不产生半成品或丢失先前用户记录。
- 查词、阅读、批注和词典导入不自动创建学习事实或知识点。
- 当前路径使用的版本发布、事务及幂等保证。重分词不覆盖用户记录或破坏已保存位置。
- 保存真实用户记录前建立受支持基线，并在隔离数据上验证备份恢复。

## 三种验证节奏

**开发循环**：只跑能证明当前修改的最小检查，失败即定位修复；不反复联跑无关套件。

**任务交付**：受影响回归、相关 lint/类型/构建及用户动作验收。前端视觉任务在每次有意义的调整后看实际页面，交付时提供代表截图。无关目录不为“凑全绿”而构建。

**阅读器里程碑**：一次完整阅读器回归与真实前后端浏览器流程。涉及共享基础模块时扩到受影响的旧功能。为审计全套跑一次可以，但不让每轮 UI 调整重复承担。此处不创建定时任务或夜间自动化。

核心浏览器流程：真实导入 → 素材库封面 → 打开章节/图片/ruby → 查词 → 跨节点划线/保存批注 → 修改显示 → 刷新与重启 → 找回位置/批注。可以早期人工复演；稳定后才把高价值路径自动化，不强制先搭全套浏览器测试框架。

## 现有测试如何减负

1. 先按能力与依赖标记：阅读核心、共享基础、暂缓学习功能、性能/兼容实验。分组是任务，不假定已存在 marker 或脚本。
2. 暂缓功能的 strict xfail 不阻塞阅读器交付，也不移除 xfail 冒充完成。当前切片相关不变量仍须有通过的语义验证。
3. 删除或合并测试须说明重复断言及保留覆盖位置。目标是减少重复维护，不能以测试数量下降作为绩效目标。
4. API 字段以生成类型为源；运行时验证保留必要的真实边界检查，避免每层复刻完整 schema。fixture 只覆盖实际使用的功能，不为所有未来页面维护身份翻译系统。
5. 旧测试若锁定已正式改变的行为，在契约决策后调整；未批准的新模型不能靠跳过失败测试落地。
6. 发现失败要区分本次回归、既有问题与暂缓功能。记录证据；不能把所有失败标成“不相关”，也不顺带开启全仓修复。

## 现有命令注意事项

2026-09-13 检查到 `frontend/package.json` 的 `pretest` 会运行 `pnpm types:check`；`pnpm test` 并非只有 Vitest。开发期定向测试可在 `frontend/` 使用 `pnpm exec vitest run <具体测试文件>`；涉及 API/生成类型或准备交付相关变化时再显式运行 `pnpm types:check`。`pnpm build` 已包含 TypeScript 检查，不必再重复同一 typecheck。

后端定向检查在 `backend/` 使用 `uv run pytest <具体测试文件> -q`。现有配置只声明 pytest；不声称已有后端 lint/typecheck 工具。这里不修改 package scripts、pytest 配置或 CI，不保证已有 E2E 命令。

## 交付证据

简短记录：用户动作与结果、修改边界、运行命令与结果、视觉/真实数据路径证据、未验证项及原因。报告测试数量可以，但不锁定某个历史数量。只做局部验证就称局部通过，不能写成全仓通过。

选择方案或优化测试前没有计时证据，就只讨论维护结构；首次做测试分组时记录基线耗时与重复检查，后续据实优化。
