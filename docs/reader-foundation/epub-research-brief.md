# EPUB 内容模型与阅读器方案调研：可直接派遣的任务说明

状态：调研委托说明，2026-09-13。用户将自行派遣 Agent。本任务不修改正式契约，不接管完整阅读器实现。

## 可复制的任务描述

你是负责 EPUB 阅读器技术方案的研究 Agent。LearningJ 目前是 React/TypeScript 前端、Python/FastAPI 本地后端与 SQLite 的项目，已有 EPUB/TXT 文本导入、Sudachi 分词、Yomitan 词典导入/查词和部分批注能力。现行 EPUB 路径主要是抽纯文本再分句，尚不足以支撑完善的图文阅读器。

现在产品优先交付 EPUB/TXT 日常阅读基座，暂缓 AI 与音视频。我们已接受「阅读内容与语言处理内容分开表示，之间保存可验证的位置映射」的方向。请研究最小可靠实现方案，以缩短真实阅读闭环与降低长期维护成本为目标。

你的交付是方案比较、受控原型证据和契约影响建议，不是直接改主线。不要为了适配新目标擅自修改 data-model、DESIGN、task-packets 或数据库。先给出最小验证计划；原型放在独立临时目录或独立工作树中，用合成/获授权样本、隔离数据运行，不覆盖用户文件，不给主项目新增依赖。

## 必须回答的问题

- 采用现有阅读渲染引擎、受控 XHTML 渲染，或现有管线渐进扩展，各自的实现/维护成本、限制和退出路径是什么？先比较少量可行路线，不罗列大量包。
- 前后端分别承担什么？书籍资源如何解析、存储、提供给渲染器？封面、目录、图片、字体、样式和链接如何保留及受控加载？
- 阅读位置和规范文本如何双向映射？明确 DOM UTF-16、Unicode code point、NFC、ruby 基文/注音、空白、隐藏节点、跨元素选区的处理。
- 同文重复出现如何消歧？不能只按 surface 找到全部匹配就当作用户选中了每处。
- 批注、查词命中和返回位置如何在重排、字号/主题变化、图片异步加载、重新打开后保持稳定？重新导入、正文变更、分词版本变化时分别怎么办？
- TXT 如何进入共同的阅读/定位接口而不伪装 EPUB？未来 AI 如何取得规范原文与位置而不依赖渲染 DOM？不需要提前实现 AI 表和状态机。
- 是否必须整书分词后才能阅读？较大章节和大量插图的首次打开/后续导航如何控制延迟与内存？
- 哪些当前能力可直接保留，哪些需适配，哪些旧约束确实必须修改？

## 最小证据集

先选择最有希望的路线做一个短原型。若失败，再验证替代路线；不要为每个候选做完整应用。

| 样本或操作 | 需要记录的证据 |
|---|---|
| 图文/ruby/目录/内部链接 | 实际渲染截图与操作结果；章节顺序、资源路径正确 |
| 重复文字、跨行内节点与跨句选区 | 选中的唯一位置、规范文本、映射回正文的一致性 |
| BMP 外日文字符、组合字符、空白和 ruby | 浏览器选区与后端规范文本对应，无错字/偏一位 |
| 字号、宽度、主题变化和图片加载 | 原有划线与返回定位不漂移 |
| 保存后关闭进程再打开 | 批注和返回位置从持久数据恢复，不依赖内存演示 |
| 大章与较多图片 | 样本规模、运行环境、首次打开与导航的测量方法及结果，不泛化为性能承诺 |
| 恶意资源路径/脚本/外链、损坏文件 | 明确拒绝或隔离结果，不执行出版物脚本、不越界读取本地文件 |
| 日文竖排 | 至少验证布局、ruby、查词定位与选区；明确未支持处 |

用少量覆盖不同风险的样本即可，不追求兼容全集。区分“实测”“文档支持”“推断”“未验证”。保留原型命令、样本来源/使用权限、截图和关键自动断言，方便复演。

## 交付形式与停止条件

1. 一页建议：推荐路线、理由、最重要的限制及放弃条件。
2. 少量方案对比：当前版本、许可证、维护现状、与现有栈关系；技术事实引用官方/上游资料，记录查证日期。
3. 内容流与位置映射示意、核心接口示例；示例是提案，不是正式字段契约。
4. 最小原型结果及复演方式，包括失败样例。
5. 契约影响清单：具体文件/章节、现状、建议变化、为什么必须变；保留不受影响的保护边界。
6. 第一个可交付纵向任务：用户动作、写入范围、依赖和最小验收；后续只列粗粒度节点。

当证据足以选择路线并暴露关键未解风险时停止。不要扩展到 AI/SRS、全量素材格式、全面重构或正式迁移。无法验证的关键点明确列为下一步，不用推测填成通过。
