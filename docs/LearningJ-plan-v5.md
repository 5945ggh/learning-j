## 0. 一句话主张

**较为方便地获取 AI 解析、便于回看地保存产生的大量解析内容、把特定解析提取为可持久化的知识点并使其再遇。**

这三件事目前在日语学习工具链中普遍空白，且对所有目标人群都成立。产品的其余部分（词典、翻译、注音）是准入条件；依存分析 + 可视化是未验证学习效用的市面空缺；原生多模态（视频、音频与文本一样都是第一公民）以及各部分的结合有潜力润滑体验，但不是绝对的差异化来源。

「获取解析」不是「获得一份讲稿」，而是**一次可追问的互动**。理由见 ADR-017——真正产生价值的常常不是解析本身，而是用户提问之后模型给出的那一段。

## 1. 受众：两个市场 + 一个留存阶段

### A 类：零基础启蒙者（N5 以下）

几乎没有活用、语用等概念，阅读理解能力接近零，极端情况下五十音未完成。不希望纯粹走 JLPT 应试路径，希望以沉浸方式优先建立实际沟通能力。

- AI 解析是**主要学习方式**，而非补充；
- 已知词表与学习数据积累少，几乎冷启动从零开始（由此，基于词汇覆盖率的「难度推荐」在这一阶段几乎失去意义）；
- **无法验证解析正确性**，见 ADR-009；
- 音视频素材对其价值主要在动机与多模态线索，语言学上的可理解度低。

**约束一**：A 类的实际可达时间晚于 B 类一个发行工程。见 ADR-020——A 类恰恰比较可能是装不动本地服务的人群，而本地后端是 ADR-010 唯一顺畅的形态。

**约束二**：A 类是**成本模型上最危险的人群**。稠密使用意味着解析次数正比于阅读句数，而会话形态又给每句加了一个可变乘数。因此「一次性完整解析是默认路径、会话是升级项」对 A 类尤其不能松。

### B 类：沉浸社群

已在使用 asbplayer + yomitan + Anki 组合，或 Migaku / LingQ 等付费产品。

- 技术能力强、愿折腾配置、付费意愿低；
- **互操作是准入条件**而非普通加分项；
- AI 解析对其价值在于「沉淀与再遇」这缺失的一环，尤其是母语文化者才能理解的社会与时代背景；
- BYOK 对其是自然的，且与开源定位自洽；
- 把学习数据通过本地 API 或 MCP 暴露出去，成本低、受欢迎；
- 主力社群以英语为母语——ADR-024 的直接依据。

### C 类：高水平语用文化读者

日语水平较高，希望进一步体会文本在母语文化语境中的额外意义。

- 值得分析的句子**他们未必能感知到**——读起来只是不明所以，甚至在不知情下误解；
- 需要的是批注与检索，**不是复习**（梗是一次性的，看懂即完）；
- 解析侧重语用、文化与互文，而非语法。

C 类在路线图上作为 B 类的留存阶段处理（ADR-001），但这不否认它作为独立需求存在。

其核心需求「要批注与检索、不要复习」由 `retention = reference` 直接承载，**这项能力在 MVP 内**，成本是一个枚举字段。推迟的只是 C 类的**发现机制**（ADR-014）。

### 明确的非目标

**应试人群不排除，但不为其做不顺路的优化。**见 ADR-012。

## 2. 交互内核

三类人群的差异不在功能清单，而在**解析的触发方式**。

| | 触发方式 | 频率 | 「主动交互即价值信号」是否成立 |
|---|---|---|---|
| A | pull | 稠密（几乎每句） | **不成立** |
| B | pull | 稀疏（卡住时） | 成立 |
| C | push | 由系统标记 | 不适用 |

**B 类**：右半屏解析视图默认折叠，AI 解析是例外路径。「用户主动付出的一次交互成本就是最干净的价值信号」在此完全成立。

**A 类**：当用户点击了全部内容时，点击不再携带信息。原计划以卡片流 + 推荐补偿，现推迟（ADR-022）。MVP 的替代方案是按顺序手动逐句解析 + **多选批量解析**。真正防止复习队列失控的机制是闸门体系（ADR-019），不依赖推荐做筛选。

**C 类**：pull 之外可能需要被动标记的辅助推送，形态为**可疑句高亮**而非「过滤后直接解析」，见 ADR-014。

### 关于「语法与单词是正确的划分吗」

结论：**它不是学习内容的划分，而是当初为了标识符空间做的划分**（词有 lemma ID，语法点没有），被误当成了前者。它漏掉了惯用搭配（気にする、腹が立つ）、缩约与音变形（〜ちゃう、〜とく）、语域与敬语级别等。

在 ADR-005 的两层模型与 ADR-034 的模式语言下，这个问题被彻底解决：`anchor_shape` 是 payload 形状判别式（pattern / lexical / entity / opaque），不是学习内容划分。GRAMMAR / MWE / USAGE 的差异是生产性程度，落在 ADR-021 的多值标签中，不进判别式。

## 3. 两个 shell，一套底座

阅读器 shell 与卡片流 shell 共享同一套数据模型、解析引擎与复习逻辑，但入口、交互与 UI 有必要做出差异。

### 素材的统一抽象

「音视频与文本同为一等公民」的可验证形式：

> **素材 = 有序 Sentence 序列 + 可选时间戳 + 可选 locator。**

差异全部落在「时间戳有没有」与「locator 指向什么」上。**上层的解析、抽取、复习、聚合不得感知素材类型。**这是一条架构约束，应写成测试。形状见 `data-model.md` §8。

**MVP 接受三种素材**：字幕文件（含挂载视频／音频）、纯文本、EPUB。PDF 走「转纯文本」降级，不做独立渲染器与锚点。

### 阅读器 shell（MVP 内）

单位是**一部作品**。左半屏阅读器／播放器（本质是字幕内容），可折叠的右半屏解析视图。A 类同样使用它自行阅读并手动控制学习，配合多选批量解析。

### 复习视图（MVP 内）

**它是 ADR-023 的试金石。**

复习视图与卡片流 shell 是同构的——都是「一个队列 + 一个组件」，区别只在队列来源与承载组件。因此先做复习视图有双重收益：

1. 自建 SRS 没有复习视图等于没做；
2. **若复习视图能在不修改任何组件的前提下装配出来，ADR-022 推迟卡片流的风险基本清零**；若装配不出来，会在 MVP 阶段而非半年后暴露 ADR-023 没落实。

### 卡片流 shell（推迟）

单位是**一次会话**。今天学 N 句，句子由推荐给出，可能来自不同材料。作品退化为素材来源。推迟理由见 ADR-022。

实现后两者互相引用：卡片背面可跳转至该句在原作品中的位置；阅读器中的任意句子可被标记进卡片流。

### 术语区分（重要）

「队列」此前指多样东西，文档中必须分开：

- **推荐分发队列**：今天学哪几句。属卡片流 shell，**推迟**；
- **SRS 复习队列**：今天复习哪些卡。**MVP 内**；
- **待确认收件箱**：异步抽取产物的兜底入口。**MVP 内**。称「收件箱」而非「队列」是有意的——见 §9，它不是待办清单。

## 4. 输入端与持久化

**接受的素材**：视频 + 字幕、音频 + 字幕、文本（纯文本 / EPUB，PDF 转纯文本）、来自其他平台的数据（Anki、jpdb）。

**视频不存副本**：媒体身份 ≠ 媒体存储。见 ADR-010。音频与文本素材单独复制一份是可接受的，但应考虑文件大小——给用户复制与否的选择权，以及本次是哪种处理模式的知情权。

**随附译文**：双语字幕的译文作为独立字段保存，解析时传入，**但必须明确标注为参考而非标准**。依据是实录中模型自发的判断——字幕组存在意译与行间未对齐，分析应优先从日文本身与上下文出发。不传译文是浪费，无标注地传译文是误导。

**Sidecar**：分句与分词结果以 messagepack 随素材持久化，必须携带内容 hash 与三个版本戳。`analyzer_dict_version` 是 ADR-018 的硬性要求：Lexeme 的自然键建立在 `normalized_form` 之上，而它会随 SudachiDict 更新漂移，不记版本则第一次升级词典就是全量脏数据。释义词典另以 `dictionary_source_id` / `dictionary_source_version` 记录，不与分析器版本混用。进入系统的文本统一使用 NFC、LF 和 Unicode code point 偏移；前端渲染时由适配层转换为浏览器所需的 UTF-16 偏移。完整文本规范化契约见 `data-model.md` §0。

内容 hash 的另一个用途是留口：将来 sidecar 可脱离本机复用（同一文件、他人已分析过的可直接取用）。零成本，现在不做。

### 原始素材保留策略

素材导入采用“原始资源、规范化文本、派生索引、用户状态”分层。

- 视频素材默认行为是只保存外部 locator，不复制视频本体。
- 视频素材、音频与文本素材（包括 EPUB）允许用户选择：
  - `external_reference`：只保存用户提供的 locator；
  - `managed_copy`：复制一份不可变原始文件到应用管理目录。
- 是否复制必须由用户明确选择，或由产品根据文件大小给出可确认的默认建议；导入界面必须说明两种模式的后果。
- `managed_copy` 只表示原始资源由应用管理，不表示修改原始文件。原始文件始终保持不可变。
- `external_reference` 模式下，用户移动或删除原始文件可能导致原始布局、图片、CSS、字体和媒体资源不可用；已生成的规范化 Sentence 与 sidecar 可以继续保留。
- `managed_copy` 模式下，后续阅读器可以从原始 EPUB/音频资源中恢复更接近原始布局的展示；派生 sidecar 仍然可以独立重建。
- `Material.content_hash` 继续表示规范化 logical text 的 hash，不改作原始文件 hash。
- 如需要校验原始文件，应额外记录 `source_sha256`；不得用原始 EPUB 二进制 hash 替换规范化文本 hash。
- `copy_stored` 必须反映真实状态，不能因为导入接口暂未实现复制而对所有素材固定写入 `false`。

## 5. 处理 pipeline 与算法／AI 的分界

### Pipeline

1. 视频 →（音轨提取）→ 音频 →（STT）→ 文本 →（处理）→ 可挂载字幕。**MVP 排除**；
2. 异构文本素材 →（处理）→ 统一的可解析文本；
3. 文本 →（算法解析）→ 结构化的 sidecar。

### 算法与模型的职责边界

可被词典与形态分析器校验的内容（分词、活用形、词典释义）**一律走算法**，模型只负责串讲、语用与文化背景。UI 上区分「查得到的」与「模型说的」。见 ADR-009。

这条边界在 v5 中被推到最强的形式：**抽取段的输出中，任何可由算法从原文推导的内容一律不由模型给出。**模型给原文子串与语义判断，字符偏移、token 区间、三元组全部由后端推导。

依存分析与翻译**先按懒生成、只缓存实现**，不持久化。这是暂定值：若性能数据显示重复生成代价过高，或依存结果被推荐算法频繁前置使用，则改为持久化。缓存 key 必须带分析器版本与词典版本。

**AI 解析不进入预处理逻辑。**这是成本可控的根本原因：成本随用户实际学习的句数增长，而非随材料长度增长。

### 分词与依存的实现

**已确定**：SudachiPy + SudachiDict，A mode。理由与代价见 ADR-018。

依存分析若进入 MVP，实质等于 GiNZA 进入 MVP。见 ADR-025 与未决事项 9。

## 6. AI 解析

形态与全部决策见 **ADR-017**；输入输出形状见 `prompt-contracts.md`。本节只留三条产品级判断。

### 6.1 为什么是文档而不是消息

一次性讲稿接不住最有价值的内容。实录中信息密度最高的一段（`よっと` / 词边界误判）完全源于用户主动说「我听成了よ！」。产品若只提供单向讲稿，这类信息结构上无处可去。

改为可寻址小节组成的文档，解决三件事：

1. **回看不再是长篇罗列。**默认视图是**原句带下划线、点哪里看哪里**，对话记录折叠。长篇大论的根源不是长度，是线性；
2. **上下文长度基本不是问题。**重放所需状态 = 当前小节集合 + 最近 N 轮往返，稳态约 5k 到 15k token；
3. **Occurrence 的内容引用有了稳定锚。**

### 6.2 为什么抽取由用户主动触发

会话形态使抽取失去了自然触发点：turn 1 后抽取会漏掉追问产生的小节（而追问恰恰是最有价值的内容来源），每轮增量抽取则成本不可接受。

因此抽取由用户点击触发，**该动作即会话终点**。这同时符合一条产品意图：AI 解析这一环节被有意设计得**重**一些，使用户重视它而非随手触发。

由此，**待确认收件箱回到了它该在的位置**——批量路径与关窗兜底的例外流入口，而非常态。

### 6.3 批量解析

多选批量必须实现为**顺序排队的多次单句调用**，不是一次大调用。理由：一次性把多句塞进同一 prompt 会同时损坏每句的前后文窗口、每句独立的抽取契约、以及 Occurrence 与句子的一一对应。排队式在成本上几乎相同，UI 上是一个带进度的列表，且天然可以边生成边读。可做适度的异步并发，提供用户可配置的最大并发数。

**批量解析不进入会话形态。**互动课堂与批量精读是两种模式，不合并——让用户对三十句逐个互动是荒谬的。

**预取**：暂时不做。后续可尝试仅在强信号下预取（某句停留超过阈值时长、或播放中的下一条字幕），设并发上限，不做滚动式全量预取。

## 7. 数据模型

**字段级契约见 `data-model.md`，本节只留两条不属于数据层的判断。**

模型的全部结构决策（两层分离、显式指认、形态规范、合并机制、形式级主键）已收进 **ADR-005**。

### 7.1 KP 的内容来源必须受控

**KP 的内容永远来自解析小节，不来自自由文本。**

这是 ADR-030 否决「提升 Annotation 为 KP」的理由：KP 要进 SRS、进导出、进聚合视图，不能有一个无任何规范约束的内容来源。用户划线后若想学它，正确动作是跳回原文位置、在阅读器中手动发起一次解析。

三者分工：**整理靠 Annotation，复习靠 KnowledgePoint，回看靠 Analysis。**

### 7.2 红线：两个数不能相加

> **词汇量统计与知识点学习进度是两个数，分别显示，永不相加，永不互相校验。**

前者是 Lexeme 层的覆盖率估计，天然模糊；后者是 KP 层的精确计数。

聚合视图中同一知识点可能同时显示「被讲解过 3 次」与「在你读过的材料中出现过 5 次」。这不是 bug，是**两个有不同标签的量**。用户完全能理解，前提是别把它们印成同一个数字。**这是一条 UI 约束**，不只是数据约束。

## 8. 复习与再现

### 「第二遍就能懂」不是自动的

解析一句是**局部**的，而听力可理解度是**整体**的：一集 300 句，精解 20 句，第二遍仍有 280 句不懂。此外，解析建立的是「读」的理解，而无字幕重看用到的是实时切分连续音流的能力，两者之间没有自动迁移。

**其一，同集内复现优先。**推荐优先选取在本集内高频（按词根统计）且用户未知的项。此项依赖推荐器，随 ADR-022 推迟，但词频统计本身在算法层是现成的，可先用于展示。

**其二，再现有声音则必带。**若自建 SRS 只复习文字，练的仍然是读。数据模型中包含句级时间戳，抽取数秒音频几乎免费。

**但 TTS 是非必须配置项**（ADR-016），因此非原生带音频的素材，其知识点卡片不一定有音频。卡片模板与 Anki 导出都必须能处理**音频缺失**。

### 复习卡片

- 正面：知识点 anchor + 例句（Span 高亮）+ 音频（若有）；
- 背面：该次 Occurrence 引用的解析小节。

卡片的形式未必要定死，提供给用户一定程度的定制化选项也会是有价值的。

**系统排程的复习卡「就事论事」**，只呈现当次实例，不堆历次。历次实例的并置属于聚合视图，不属于复习流。

### 聚合视图

用户主动查询某知识点时，展示该知识点下的历次 Occurrence 并置。

**它不是一个新界面**：候选确认时「悬浮展示相近知识点卡片」的浮层就是它的最小形态，主动查询入口只是把同一组件放大成面板。

聚合的 key 是 KP ID（经 canonical 视图归并）。同时显示的两个计数必须分别标注来源，见 §7.2。

**灵感（未排期）**：以各学习材料为中心节点伸展出知识点图，展示 `canonical_id` 指向等信息，支持按标签与学习状态筛选。

### 语法 KP 的再遇率结构性偏低

词汇类 KP 有 `lexical_anchors`，再遇可由算法免费触发；**语法类 KP 没有可匹配的算法锚，只有在下一次 AI 解析恰好又抽到它时才会再遇。**

这是模型的结构性事实，不是抽取质量问题——必须写在这里，否则实际使用时一定会被误判。

缓解手段是为高频语法锚写模式匹配规则，**但它不在 MVP 内**（`prompt-contracts.md` §4.1）。这是一个已知且接受的代价。

### 活用覆盖

在词根频次之上，推荐进一步覆盖**同一词根的不同活用形**。完全落在算法层，Sudachi 输出中辞書形与活用形均为现成字段。这是 ADR-006 中已知状态粒度要求的直接来源。

TTS 在此有一项原声无法替代的价值：**原声只能给出素材里出现过的句子，TTS 能给出任意词形的读音**。

### 听力

**提议**：先做最退化的形态——同一句先只放音频，用户自评能否听懂（或听写，待定），再展开文本与解析。完整题型系统（出题、判分、反馈）会把产品从辅助器推向课程，待前者被验证有人用之后再议。TTS 音频可以进入这一流程，但记为不同来源与置信度。

### Anki 挖矿

支持导出整句卡与知识点卡，带音频、图片，视频切片作为可选配置项。不指定固定格式，只需暴露字段供用户主动选择、与 Anki 条目对应。系统内部的卡片也应允许用户自由配置。

**导出流程刻意保留一点摩擦。**见 ADR-013。

## 9. 候选与筛选

### 候选显著性与排程优先级

用户主动触发抽取时走 **triage 页**，逐条决定是否排程复习。「不学」即写入 `retention = reference`——KP 照建、照进聚合与检索与记忆注入，只是不排程复习。这里的 `reference` 是用户的排程选择，不是模型对「一次性文化梗」等内容类别的判断；只要模型将内容抽取为候选，就应交给用户决定是否加入复习，不适合形成可复习知识点的内容才留在 Analysis 中、不进入 KP 候选。

批量与关窗兜底路径没有 triage，此时所有已抽取候选默认取 `retention = srs`；`salience` 只决定 ReviewItem 的创建优先级：`primary`（收尾小节点名的 1 到 3 条）优先，`secondary` 列出并留在待建队列中。后续用户仍可在收件箱中将任一 KP 改为 `reference`。

**修订理由**：实录显示单句可抽出十条以上候选（仅「汚い、素人相手に変化球使うなんて」一句即有 `汚い` 引申义、`素人`、`N相手に`、`を` 脱落、`普通形 + なんて`、`なんて` 结句、ワ行五段、听感助词消失等）。若默认全部加入，待确认收件箱会以每句十几条的速度增长，用户永远处于欠债状态。

**不违反 ADR-019 的精神**：Occurrence 仍无条件全记、永不去重，`salience` 只改变 ReviewItem 的创建优先级，不改变 KP / Occurrence 的存在。

### 不做硬性去重

即使规范书写完全一致的知识点，在不同语境下也可以表示不同意思、具有不同语感；且即便确属重复，新例句本身也是有价值的资产。

替代方案是**提示而非拦截**：候选项上做超链接式标记，悬浮展示已有的相近知识点卡片（即聚合视图的最小形态）。

真正需要控制的不是候选数量，而是复习队列的增长率——由 ADR-019 的每日配额与「每 KP 一条」共同解决。

### 待确认收件箱不是待办清单

它只展示尚未由用户决定排程意愿的抽取产物，不做未读计数，不做红点。用户在 triage 或收件箱中选择「学」或「不学」后，该候选从默认收件箱消失；已处理产物的历史查看通过 ExtractionRun、Analysis 与 KP 聚合视图完成，不通过收件箱完成。**这一条必须写进 UI 规格**，避免把收件箱实现成待办清单。

列表按 KP 折叠，同一 KP 的多条 Occurrence 显示为一行 +「再遇 n 次」。

### 推荐（随卡片流一并推迟）

推迟内容：选择与推荐算法、知识点密度估计。可用的估算量记录备查：

- （陌生）词汇数、句长、依存树形态、是否含未见过的活用形；
- 由上述结合用户学习历史估算的**知识点密度**（此处「知识点」指算法可估的语言点，非最终产出的 KnowledgePoint，不保证准度）；
- 同集内词根频次与活用覆盖。

## 10. 互操作

范围：导入既有 Anki / jpdb 已知词表、导出卡片到 Anki、兼容 yomitan 词典格式、其他数据的导入导出、通过本地 API 或 MCP 暴露学习数据。

**时序：部分后置，但证据模型先行。**见 ADR-011。

冷启动有第二条路：阅读行为本身即产生已知状态证据（划过不查的词、解析中标为已知的词）。因此互操作是「加速冷启动」，而非「让功能可用」的前提。

**关于 lemma_id**：失去 UniDic 語彙素对互操作**没有损失**。Anki 按字符串字段匹配，jpdb 用自己的 vocab id，yomitan 词典按表记加读音索引——整条链路上没有任何一环认 UniDic 語彙素。损失只发生在站内自身的同一性上，已由 ADR-018 与 ADR-005 处理。

导入的已知词表落在 **Lexeme 层的 KnownEvidence**，来源标记为 `import_anki` / `import_jpdb`。它**不产生 KnowledgePoint**——导入不是指认。

**高价值目标**：兼容 Yomitan 词典格式。MVP 将 Yomitan ZIP 作为用户词典的第一等导入格式；导入后进入内部 canonical dictionary model，不把 `term_bank` 结构泄漏到业务层。每个查询结果带词典来源与版本，并同时保留纯文本定义和可选 structured content。原始 JMdict XML、EPWING、MDX 等格式通过未来的 importer adapter 接入，不阻塞 MVP。

查词交互不占用浏览器 Yomitan 的 Option/Alt + hover 手势。LearningJ 采用显式点击或键盘选择 token：宽屏优先在阅读器右侧打开 DictionaryDrawer，空间不足时使用锚定 DictionaryPopover；Escape 关闭后焦点返回触发 token。查词是轻量、可撤销的阅读动作，不自动创建 KnowledgePoint 或 ReviewItem。

> 术语澄清：「难度标注」指依据用户已知词集合对材料／句子给出难度。已知集合为空时所有材料都显示为近乎全生词，标注失去区分度。阅读行为推断可以逐步填充该集合，故该功能是「初期效果差」而非「不可用」。

> **注**：yomitan 格式词典的**内容**（各家词典）多数不可再分发；VOICEVOX 的角色音源有单独使用规约。开源发行版打包时会撞上，提前记录。

## 14. MVP 边界

### 保留

- 阅读器 shell + 句级 AI 解析（含多选批量解析）
- **解析为可交互文档**：小节化、Span 索引、追问追加小节、对话记录持久化
- **用户主动触发抽取 + triage 页**
- **算法基础解析**：分句、分词、注音、词典查词、翻译
- 两段式解析（生成 + 抽取）与待确认收件箱
- **两层数据模型**：Lexeme 层（证据、统计）与 KnowledgePoint 层（学习）
- 知识点规范化（形态规范 + 自签发 ID + 别名映射，语法侧从 JLPT 语法表起步做种子）
- Annotation（划线 + 批注 + 检索 + 跳转，支持跨句）
- 记忆注入（KP 检索 + 两类笔记，槽位上限）
- 自建 SRS + 配额 + 每 KP 一条 + 句级音频再现（有则带）
- **复习视图**
- 聚合视图（含浮层最小形态）
- Anki 导出
- Python + FastAPI 后端与 sidecar 持久化
- 素材类型：字幕 + 纯文本 + EPUB

### 条件式

- **依存分析 + 可视化**：可视化成本不高（日语文节依存严格右向、非交叉，是一维弧线图而非通用 DAG 布局），但实质门槛在上游——文节切分与 GiNZA 引入。见 ADR-025 与未决事项 9。

### 排除

- STT pipeline（生肉处理）
- **解析小节的 agent 改写与合并**（`revise` / `merge`）——schema 第一天就有，行为放第二阶段
- **高频语法锚的模式匹配规则**——代价见 §8
- **抽取写入时的 alias 查重**——由 top-k 候选检索在抽取前解决
- PDF 独立渲染器与锚点（走转纯文本降级）
- 卡片流 shell、推荐分发队列、知识点密度估计（ADR-022）
- 解析共享后端
- 完整听力题型系统
- C 类发现机制（ADR-014）
- 解析时的联网检索（但 `retrieval_enabled` 字段留位）
- UI i18n（解析输出语言不在此列，见 ADR-024）

### 不可推迟的数据层事项（改起来最贵）

1. **Lexeme 层与 KnowledgePoint 层分离**
2. 已知状态存为证据记录，不存字段，**目标为 Lexeme**，粒度到 Lexeme + 活用形集合
3. Occurrence 记录来源元数据
4. **所有 Lexeme 记录与 sidecar 带词典／分析器版本戳**
5. KnowledgePoint 的合并机制（`canonical_id`）从第一天就存在
6. Analysis 与 Occurrence 分开持久化
7. **ExtractionRun 独立记录每次抽取尝试**，支持失败审计与不覆盖用户决定的重跑
8. **Span 为共享值对象**，物理上使用独立 `spans` 表与各实体的显式关联表；Occurrence / Annotation / AnalysisSection / 未来的可疑句高亮共用
9. **AnalysisSection 可寻址**（`section_id` + `revision`），每个 revision 为不可变物理行，Occurrence 引用 section 而非字符区间
10. **`salience` 与 `retention` 两个枚举字段**
11. **Sentence 的锚点两段式形状**（`anchor_type` + `anchor_payload`）
12. 解析视图与复习组件独立于 shell（ADR-023）
13. **KnowledgePoint 的锚点两段式形状**（`anchor_shape` + `anchor_payload` → 派生 `anchor`）
14. **Occurrence 的 `spans` 为有序数组**（物理上 `occurrence_spans` 关联表带 `ordinal`）

## 15. 未决事项

> 全项目唯一的 open items 索引。ADR 与 spec 中不再重复维护待定清单。

1. **解析模块的默认组合**——已给临时值（`prompt-contracts.md` §1），待 `spike-checklist.md` 实验 5 回写
2. **依存分析结果的持久化与否**——暂定懒生成、只缓存，待性能数据
3. **后端的分发方式**（本地服务 / 打包发行版 / 托管）——见 ADR-020，直接决定 A 类可达时间。本地运行形态的 BYOK provider 配置与密钥存储机制已经确定，不随本项重开；若选择托管后端，服务端密钥托管另作安全决策
4. **模式语言的枚举覆盖率与边界**——category / form 的六 + 八是否够用，由 `model_chosen` 的 opaque 率决定是否扩充；`Clause` 与 `V` 的边界、`none` form 的语义（改名为 `unrestricted` 或保持但明确文档）在 `grammar_enums_v1.yaml` 中定义；已给临时规范（`prompt-contracts.md` §7.1），待 `spike-checklist.md` 实验 2 产出决策表
5. **平台其他盈利点、流量变现**——保持已有提议，暂不讨论
6. **算法层解析的能力边界**——词向量、相关性、检索、推测等，另行探索
7. **AI 解析之外的 KP 构造路径**——实质能力需求是「用户在 Span 上发起一次显式指认」，内容来源待定。可能方向：对该 Span 的一次微型解析。**不阻塞 MVP**
8. **依存分析是否进 MVP**——ADR-025 仍为提议状态，需按「GiNZA 是否进 MVP」的口径拍板
9. **B 类的准入路线**——自建播放器（需达到 asbplayer 水准）vs 承接 asbplayer / yomitan 已有工作流的下游（接住其导出的句子与截图，专注解析、沉淀、再遇）。后者砍掉大量工作且与「互操作是准入条件」自洽，代价是失去阅读体验控制且 A 类不可用。**尚未讨论**
10. **BYOK 未配置时的降级路径**——AI 解析与抽取暂不可用，但完整浏览、算法查词／词形分析、Annotation 与 KnownEvidence 仍可用；需在 onboarding 设计时正面处理何时提示配置以及如何从降级路径恢复
11. **跨语言扩展的命名空间**——当前 `pattern_grammar_version` 默认日语（格式 `0.1`）；若支持其他语言，改为 `{lang}_{version}`（如 `ja_0.1` / `zh_0.1`）。MVP 不涉及。

> 原第 8 条（素材类型范围）已结：MVP 为字幕 + 纯文本 + EPUB，PDF 转纯文本降级。EPUB 锚点 payload 已定，见 `data-model.md` §8.2。
>
> 原附属于第 3 条的本地 BYOK 密钥存储问题已结：普通 provider 配置与秘密物理分离，系统 keyring 优先，独立 0600 secrets 文件为显式降级。见 ADR-020。
