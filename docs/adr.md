## ADR-033 原始素材保留与派生索引分层

**状态**：已接受

### 决策

1. 原始素材、规范化 logical text、分句/分词 sidecar、用户学习状态彼此分层。
2. 视频默认采用 external reference，不复制视频本体。
3. 音频和文本（包括 EPUB）支持 external reference 与 managed copy 两种模式。
4. managed copy 的原始文件不可变；任何 reader 注入、渲染适配或索引生成都不得原地改写源文件。
5. `content_hash` 继续表示规范化 logical text；原始文件校验使用独立的 `source_sha256`。
6. sidecar 可以保存 native ruby hints、结构边界、sentence ranges 和 token ranges，但不保存 XPath、DOM path 或渲染后的 span 结构。
7. 必须让用户知道本次导入是 external reference 还是 managed copy，以及文件大小和后续可用性影响。

### 后果

- external reference 体积小，但源文件移动后原始布局资源可能不可用。
- managed copy 便于离线阅读、稳定复现和更接近原 EPUB 的 layout，但会占用磁盘空间。
- 规范化 Sentence 和 sidecar 不依赖 DOM 结构，可以在源文件不变时重新生成。

## ADR-032　词典交换格式与查词交互边界

**状态**：已接受

### 决策

1. MVP 将 **Yomitan ZIP** 作为用户词典的第一等导入格式；原始 JMdict XML、EPWING、MDX 等通过未来的 `DictionaryImporter` adapter 接入，不在 MVP 同时实现。
2. Yomitan 是交换格式，不是内部业务模型。导入后落入 `DictionarySource`、`DictionaryEntry`、`DictionaryDefinition`、`DictionaryAsset` 与 `DictionaryImportRun` 等 canonical 实体；定义同时保留纯文本投影和可选 structured content。
3. Sudachi 的 `analyzer_dict_version` 与释义词典的 `dictionary_source_version` 使用不同命名空间。词典条目不创建 KnowledgePoint；查询结果必须显示来源与版本。
4. LearningJ 不占用浏览器 Yomitan 的 Option/Alt + hover 手势。MVP 查词采用**显式点击/键盘选择 token**：宽屏优先打开右侧 `DictionaryDrawer`，空间不足时打开锚定 `DictionaryPopover`；Escape 关闭并把焦点还给触发 token。
5. LLM 采用内部薄 provider contract，官方 SDK 只存在于隔离 adapter 中：OpenAI-compatible 使用 `openai`，Anthropic / Google 为可选 adapter，特殊端点保留 `httpx` fallback。业务层只依赖统一 `ChatResult`，不依赖任一家 SDK 的 response 类型。

### 取舍

Yomitan 统一了多词典导入和富文本定义能力，同时避免在 MVP 为每一本词典维护专用 parser。代价是需要处理 ZIP 安全、schema 版本、来源追踪和多词典排序。显式点击查词牺牲了 hover 的瞬时性，但避免与已有浏览器扩展冲突，并能在触摸设备、键盘导航和无扩展环境中保持一致。

### 落点

`docs/mvp-tech-and-phases.md`、`docs/data-model.md`、根目录 `DESIGN.md`。

## ADR-005　知识点的身份模型

**状态**：已接受（形态规范未定，见未决事项 4）

**吸收**：ADR-004（KP 为全局实体）、ADR-026（两层分离）、ADR-027（显式指认）

### 背景

语法点没有通用标识符空间，模型对同一语法点的命名会漂移。而更根本的问题是：词汇与语法点是否是同一种实体。

### 分界依据

> **自动解析永远无法确定这个词在这里的意思。**

分词器与词典能回答「这是什么词」（含全部候选释义），回答不了「这里在讲什么」。后者只有被讲解才存在。因此二者不是同一种实体，不该共用 ID 空间。

若共用，会得到一个荒谬推论：阅读推断产生的已知状态证据指向三元组主键，而后者是 KnowledgePoint，于是**用户读过的每个词都会创建一条知识点**，一部小说一万条量级。

### 决策一：分为两层

| | Lexeme 层 | KnowledgePoint 层 |
|---|---|---|
| 构成方式 | 算法自动生成 | **显式指认** |
| 数量级 | \(10^4\)–\(10^5\) | \(10^2\)–\(10^3\) |
| 身份来源 | 词典（确定性派生 id） | 我们（自签发 id） |
| 别名与合并 | **不需要** | 需要 |
| 承载 | 查词、词形分析、已知状态证据、词频与覆盖率、难度标注 | SRS、Anki 导出、聚合视图、再遇、标签 |

两层之间是**引用关系，不是继承关系**。KP 可挂若干 `lexical_anchors`（可空、可多），**仅作索引，不参与身份判定**。

### 决策二：KnowledgePoint 由显式指认构成

> **一条 KP 的存在，前提是有人指着句子里的某处说「这里有个东西值得你学，它是这个意思」。**

被排除的是被动的、自动的创建：读过不创建，查词不创建，导入词表不创建。**MVP 内唯一的指认来源是解析抽取。**

这里的「值得你学」描述的是“该内容是否构成一个可以被解释、定位并复习的知识点”，不是模型替用户决定是否排程。只要抽取段将内容列为候选（包括文化梗、互文或元技能），就进入候选确认流程并交给用户选择；不适合形成可复习知识点的内容才留在 Analysis 中。

### 决策三：KP 为全局实体，出现记为 Occurrence

「全局」指 ID 空间全局，**不指「用户的学习范围全局」**。用户的学习本身可以有范围——单独学习某部作品中产生的 KP，或主动选择全局范围。范围是查询与筛选条件，不是身份属性，因此不进 KP 实体。

「再遇」即对 Occurrence 按知识点做的查询。Occurrence 无条件记录、永不去重，闸门在别处（ADR-019）。

### 决策四：形态规范 + 自签发 ID + 别名映射

1. 定义**形态规范**，约束知识点名称的书写形式，例如 `〜xxxx`、`V + xxxx`、`V辞書形 + xxxx`；
2. 由抽取段在规范约束下「**选择 + 组合**」出符合要求的字段；
3. 以该规范串为自然键，**自签发 ID**；
4. 维护**别名映射表**，把变体写法收敛到已有 ID。

**注**：本决策的锚点书写形式部分已由 ADR-034 替代为模式语言 + shape 判别式；自签发 ID 与别名映射机制（决策的后半部分）不受影响。

**词汇类与语法类一视同仁**：词汇类 KP 的自然键同样是锚点串，而非三元组。三元组属于 Lexeme 层，不进此机制。

由此得到一个重要推论：若 AI 讲的是「食べちゃった 里的 ちゃう 表示遗憾」，抽取产出的锚点就是 `〜ちゃう`，而不是 `食べる` 的某个变体。**锚点反映的是讲解的重心，不是分词器的切分。**

### 决策五：主键是形式级，不是义项级

同一形式的不同含义（`〜てしまう` 的「完了」与「遗憾」）共享同一个 ID，义项差异保留在各条 Occurrence 的解析片段里。聚合视图把它们并置展示，差异不但没被磨平，还成为学习内容本身。

同一次解析可以从同一个 Span 上产出多条 KP（`食べる` / `〜ちゃう` / `食べちゃう`），彼此不冲突。需要约束的是「同一次讲解不要把同一件事写成三个抽象层级」，那是形态规范决策表的活，不是数据模型的活。

### 决策六：合并必须可后补，且不可破坏

自签发 ID 意味着「新建条目」不可避免，因此**两条 ID 事后被发现指同一事物**也不可避免。处理方式与 ADR-006 的证据模型同构：**永不原地改写**。

- KP 带 `canonical_id`，合并即把一条指向另一条；
- Occurrence 保持指向它当初指向的 ID，查询时经 canonical 视图归并；
- 合并可撤销。

不这样做的话，第一次误合并就是不可逆的数据损失。

### 核心原则

> **归一化的对象是锚点，不是内容。**

用户点开一个知识点看到的不是权威定义，而是历次遇到它的实例并置，各自带着当时的解析。

### 注（撰写者保留意见，三点）

**其一，形态规范约束的是形状，不是同一性。**两个都合规的串仍可指同一事物：`V辞書形 + ことができる` / `V + ことができる` / `〜ことができる`。命名漂移由此转化为**抽象层级漂移**，并未消失。缓解手段是规范里附一张**决策表**，使每个点只有一种合规写法。见未决事项 4 与 `spike-checklist.md` 实验 2。

**其二，把抽取做成检索增强的「选择」而非开放「生成」。**抽取前先用模糊匹配从既有 KP 中取 top-k 候选一并交给模型，指令为「复用其中之一，或在都不合适时按规范新建」。这是把开放生成压回接近闭集选择的最便宜手段，也是别名表能自然增长的来源。落点：`prompt-contracts.md` §5.3。

**其三，冷启动。**第一天别名表为空，而早期数据恰恰最噪。从 JLPT 语法表起步做**种子条目 + 种子别名**，但它不再是封闭目录，只是初始化数据。

### 已否决的第二指认来源

**以词典义项选择为内容来源**（「挖矿型 KP」）。否决理由：它把**词典厂商的义项切分变成 KP 的内容边界**——该切分不由我们控制、不面向学习、随词典版本漂移。这与「归一锚点不归一内容」冲突，也与 ADR-009 冲突（「这里是哪个义项」不是查得到的，是判断）。

AI 解析之外的 KP 构造路径见未决事项 7。实质能力需求是「用户在 Span 上发起一次显式指认」，内容来源待定。

### 代价与后果

1. 引入持续的人工维护（合并、归类）。回报是该资产使「语法覆盖率」成为可能——这是 jpdb 结构上做不到的。
2. 别名与合并机制的规模从 \(10^5\) 降到 \(10^3\)。
3. 词典升级对 Lexeme 层是**版本迁移映射**，不是合并。
4. **词汇量统计与知识点学习进度成为两个数**，必须分别显示、永不相加。见 `data-model.md` §10。
5. **BYOK 是 AI 核心循环的前提，但不是产品整体可用性的前提**。未配置 BYOK 时，MVP 仍允许完整浏览、算法查词与词形分析，并可积累 Annotation / KnownEvidence；只是暂时不能生成 AI Analysis、抽取 KP 或进入 AI 驱动的沉淀环节。onboarding 仍需正面处理这一分支，见未决事项 10。
6. 用户的即时查词、词形分析、划线批注均不产生 KP，只产生 KnownEvidence 或 Annotation。
7. 导入的已知词表不产生 KnowledgePoint——导入不是指认。

## ADR-009　可校验内容交给算法，UI 区分来源

**状态**：已接受

**背景**：幻觉风险在人群间高度不对称，A 类完全无法识别，而他们恰恰把解析当作主要学习方式。

**决策**：

1. 分词、活用形、词典释义走算法与词典资源；模型只负责串讲、语用与文化背景。UI 上明确区分「查得到的」与「模型说的」。
2. 「串讲」不是让模型严格复述算法解析结果，而是在给定规范与标准下自由发挥。
3. **抽取段的输出中，任何可由算法从原文推导的内容一律不由模型给出。**据此划界：
   - 模型给出**原文子串**与**语义判断**（anchor、tags、salience、brief）；是否排程复习由用户或无 triage 路径的系统默认值决定，不由模型把候选划分为「可复习」与「不可复习」；
   - 字符偏移、token 区间、`normalized_form / POS / reading_form` 三元组，全部由后端从原文与 sidecar 推导。

第 3 条的理由：模型会写出看似正确、但与 SudachiDict 字段不严格对齐的内容，进而污染别名表；而字符偏移的典型失败模式是「整体偏了两位」，偏移后 span 仍落在句内、仍能与某个 token 对齐，是**静默错误**，会一路污染到复习卡高亮。子串定位的失败（找不到）则 100% 可由代码检测。

**代价与后果**：要求呈现层能混排两类来源的内容。

**落点**：`prompt-contracts.md` §5.2、`data-model.md` §1。

## ADR-014　C 类发现机制：可疑句高亮 + 单条反馈，整体后置

**状态**：提议（且明确后置，不在 MVP）

**背景**：C 类未必总能感知哪里有梗，系统 push 是有必要的补充；但全量 AI 解析成本正比于句数，不可行。

**决策（提议）**：

1. 用廉价信号过滤候选句（NER、语域突变、流行语词表、回译语义距离）；
2. 形态为**高亮标记**，而非过滤后直接解析——更省、更安全；
3. 必须配总开关、可调阈值、以及单条「这里没有」反馈。

**关键点**：误报形态因此改变。解析的误报只是多点开一次；高亮的误报是**正文上的持续视觉噪声**，烦人程度高一个量级——这是必须有开关与阈值的原因。同一机制在不同人群上设不同阈值（C 类容忍度高，A 类宁可漏不可错）。

**副产品**：单条反馈是免费的种子数据，见 ADR-003 留口。

**约束**：高亮的位置表达必须复用 Span 值对象，不另起一套。

## ADR-016　TTS 与原声是语体差异，不是质量差异

**状态**：已接受（选型待调查）

**背景**：曾以「TTS 音高重音常错、语速匀整」为由禁止 TTS 进入听力自评流程。该理由**事实层面不成立**——本地可部署级别的 TTS（如 VOICEVOX）质量已普遍不错，速度、语气可调；第三方 API 更强。

**决策**：

1. 撤销「TTS 不进入听力自评流程」的禁令。
2. TTS 与原声的真实差异是**语体**而非质量：合成语音是朗读体，发音完整、不吞音、不重叠、无环境声、语速匀整；而听力的真正难点在连读、缩约、抢话与噪声，调快朗读语速并不产生这些现象。
3. 该差异由**证据模型**表达而非由禁令表达：听懂 TTS 与听懂原声记为不同来源、不同置信度（`listening_tts` / `listening_native`）。
4. **撤销「校验 TTS 音高重音」的提议**——难做且无明确收益，属过度设计。
5. TTS 是**非必须配置项**。因此非原生带音频的素材，其知识点卡片不一定有音频；卡片模板与导出必须处理缺失情况。

**新增的正面价值**：原声只能给出素材里出现过的句子，**TTS 能给出任意词形的读音**。活用覆盖推荐所需的词形在原声素材中未必存在，TTS 是唯一来源。

**待调查**：具体选型。VOICEVOX 仅为举例，注意其角色音源有单独使用规约，开源发行版打包时需处理。

## ADR-017　AI 解析的形态：可交互文档 + 两段式

**状态**：已接受

**吸收**：ADR-028（撤销标题层级契约；解析为可交互文档）

### 决策一：两段式

- **第一段（生成）**：主模型在给定规范与标准下自由发挥。上下文为原句 + 前后文 + 译文 + 用户困惑 + 模块开关 + 记忆注入。
- **第二段（抽取）**：依知识点规范抽取结构化信息，经规范层映射为 KnowledgePoint。

### 决策二：第一段正文不受语义结构契约约束，但保留最小寻址标记

曾要求第一段以标题层级承载结构契约，供下游抽取定位。实证数据（`网页对话版本的例句解析实例.md`）表明：前沿模型在高 thinking effort、单次长输出内部，会把并列小节写成 `#` 与 `##` 混用。这类失败率不低、无法可靠检测，而整条抽取链路曾押在它上面。

替代方案**不是**把契约挪到文末哨兵块——那等于把 JSON 换个位置，仍会反向绑架写作，正是否决直出 JSON 的同一条理由。而是：

- 第一段的讲解内容、语义组织和小节顺序完全自由，只增加用于后端寻址的最小 heading-id 约定，并要求以一个「本句最值得带走的东西」小节收尾（实录显示这是模型的自发行为，不需要复杂诱导）；
- heading id 只用于定位，不承担 `kind`、Span 或知识点语义；重复或缺失时允许后端降级；
- 一切机器可读的结构由第二段产出。

**连带撤销**：「解析风格档位与抽取契约绑定」不再必要，风格退化为**模块开关**。实录同时证明硬档位是错误方向——一次面向低水平学习者的解析里出现了《こころ》互文，**好的解析本来就跨档位**，用互斥预设去切它会切坏。

### 决策三：解析是文档，不是消息

一次性讲稿接不住最有价值的内容。实录中信息密度最高的一段（`よっと` / 词边界误判）完全源于用户主动说「我听成了よ！」。产品若只提供单向讲稿，这类信息结构上无处可去。

因此：Analysis 的正文由若干可寻址的 **AnalysisSection** 组成，每个小节声明覆盖的 Span（可空）。用户可在同一 Analysis 上追问，产生新小节（MVP）或修订／合并已有小节（第二阶段）。

### 决策四：不依赖 tool calling

BYOK 下模型能力分布不均，多轮工具调用是高风险依赖；而一两千 token 的文档不需要文件编辑工具。改写以**结构化输出**表达（按小节 id 返回操作）。

真正的工具（查词典、检索已有 KP 库）可以有，但必须设计成缺失时降级仍可用。

### 决策五：抽取的触发时机

> **抽取由用户主动触发，该动作即会话终点。**

```
生成解析 → [用户读，可追问 N 轮] → 用户点「提取知识点」→ 抽取 → 候选 triage → 决定学 / 不学
```

理由三条：

1. 决策三让抽取失去了自然触发点。turn 1 后抽取会漏掉追问产生的小节，而追问恰恰是最有价值的内容来源；每轮增量抽取则成本与复杂度都不可接受。
2. 会话终点从此有定义，`turn_count` 冻结，重放状态明确。
3. AI 解析这一环节被有意设计得**重**一些，使用户重视它而非随手触发。「提取」这个动作本身就是这种重量的一部分。

**提取后禁止继续追问**，会话关闭。需要补充时重新发起一次解析。

**两条例外路径**：

- **批量解析**不开会话，抽取自动执行，产物直接进收件箱；所有候选默认允许进入复习体系，`salience` 只决定 ReviewItem 的创建优先级。这是 `salience` 在有了用户 triage 页之后仍然必要的主要理由。
- **用户读完即关窗**时后台补跑一次抽取，同样入收件箱。这是兜底，不是主路径。

由此，**待确认收件箱回到了它该在的位置**：例外流的兜底，而非常态入口。

### 决策六：第二段的 prompt 必须自足

**执行路径两条**：

- **续轮**（默认快路径）：在第一段的会话基础上新开一轮，同模型执行。优势是同一模型在同一语境里知道自己刚才指的是什么。
- **独立调用**（必须支持）：输入为「解析全文 + 规范 + 候选 KP」，不依赖会话历史。

**注**：身份消解轮的执行路径与触发条件见 ADR-035。

这条约束一写死，抽取规范升级后的批量重抽、以及模型不支持长会话时的降级路径就都免费了。

**关于缓存**：缓存有 TTL，批量重抽必然冷启动，BYOK 下用户 provider 未必支持缓存。**缓存是优化，不是架构前提**；续轮的理由是质量而非成本。

**已知风险**：同会话模型有自洽倾向，可能过抽（把自己写过的全抽出来）并降低复用率（沿用自己的措辞而非库内已有 anchor）。见 `spike-checklist.md` 实验 1。

### 决策七：持久化分三档

1. 解析文档持久化；
2. 用户可见的对话往返持久化（用户的提问本身是学情信号）；
3. agent 内部轨迹不持久化（debug 开关除外）。

**Analysis 与 Occurrence 必须分开持久化**，以支持「重跑抽取」与「批量重抽」。

### 备选方案（否决）

- 要求模型直接输出 JSON——很可能损害生成质量并使解析变得死板；
- 一般层 / 实例层——见 ADR-002；
- 文末哨兵块作为硬性提取范围上界——见决策二。

### 代价与后果

1. 抽取成为解析到知识点的唯一通道，因此规范层的质量直接决定沉淀质量；
2. **成本模型多了一个乘数。**因此「一次性完整解析是默认路径、会话是升级项」成为硬约束，且**批量解析不进入会话形态**。绝大多数 Analysis 的 `turn_count` 为 1，这是设计意图而非退化；
3. **Occurrence 的内容引用必须是 `section_id + revision`**，不能是指向可变 blob 的字符区间；
4. AnalysisSection 的旧版本与被合并小节**永不删除**，否则已有 Occurrence 引用会悬空；
5. 需要新的回看视图：默认不是线性长文，而是**原句带下划线、点哪里看哪里**，对话记录折叠；
6. 上下文长度可控：重放所需状态 = 当前小节集合 + 最近 N 轮往返，中间轮次可安全丢弃。稳态约 5k 到 15k token。

## ADR-020　后端为 Python + FastAPI；分发方式待定

**状态**：已接受（分发方式待定，见未决事项 3）

**决策**：

- 基础算法解析在 Python + FastAPI 后端处理（SudachiPy、GiNZA 均在此生态）；
- 分句、分词结果作为 sidecar（messagepack）随素材持久化；
- 翻译与依存分析懒加载；
- **LLM API 调用放在 Python 后端**——除生态理由外，抽取段本就在后端，两段同侧使 prompt 版本、模型标识等元数据只有一个记录点。会话状态管理与记忆槽位校验同理。

**待定：分发方式。**

- **本地后端**：BYOK 密钥不出本机，与开源定位自洽，且是 ADR-010 唯一顺畅的形态。代价是要求用户装 Python 环境，或由项目出打包发行版（Tauri + sidecar，体积数百 MB 起）。
- **托管后端**：安装成本为零，但需代持用户 API key，且本地视频文件路径访问走不通。

**BYOK 配置与密钥存储（已定，实现约束）**：配置以 provider profile 为边界，而不是把单个模型写死在应用设置里。每个 profile 使用不可随显示名变化的稳定 `provider_id`，普通配置保存 `name`、`base_url`、`model_list` 与 `credential_ref`；应用可以尝试从 provider API 拉取模型列表，但必须允许用户手工维护。`api_key` 在逻辑上属于该 provider profile，在物理上不得写入普通配置：本地运行时以 `provider_id` 为索引优先存入系统 `keyring`；keyring 不可用时，才降级写入同一应用配置目录下独立的 secrets 文件，并在 POSIX 平台创建或校验为 0600，同时向用户明示安全降级。普通配置的同步、导出与诊断包默认排除 secrets 文件；密钥不得进入 Analysis、ExtractionRun、日志或错误消息。若未来采用托管后端，服务端密钥托管需另作安全决策，不得把本地降级文件方案直接搬到服务端。

**后果**：B 类可以直接跑裸 FastAPI，A 类必须等打包发行版。**A 类的实际可达时间比 B 类晚一个发行工程。**

## ADR-025　依存分析进 MVP 实质等于 GiNZA 进 MVP

**状态**：提议（条件式，**尚未拍板**，见未决事项 9）

**背景**：曾判断依存可视化成本高。该判断被推翻——日语文节依存**严格右向、非交叉**，因此布局不是通用 DAG 布线问题，而是一维序列上的弧线图。可视化确实便宜。

**但真正的成本在上游两件事**：

1. **文节切分**。Sudachi 给的是短单位，不给文节。要么自写文节合并规则，要么引入 GiNZA——它建立在 SudachiPy 之上，与 ADR-018 的选型天然一致。代价是模型包体积（ja_ginza 数十 MB 起）。
2. **长句在窄屏上的可读性**。二三十个文节的句子弧线图很快不可读，需要折行或聚焦模式。这是真正会反复调的地方。

**决策（提议）**：依存分析是否进 MVP，按「GiNZA 是否进 MVP」的口径评估，而不是按「画图难不难」评估。

> **注（撰写者保留意见）**：依存分析的学习效用未经验证，加上本 ADR 列出的两项真实成本，倾向于建议直接将本 ADR 状态改为**暂缓**、排除出 MVP。理由完全来自文档自身已写下的论证，不需要新信息。

## ADR-029　记忆分为作品笔记与学情画像，槽位上限由后端强制

**状态**：已接受（效果待 `spike-checklist.md` 实验 3 验证）

**背景**：实录中模型承诺并兑现了跨句记忆（第一次拆细、之后简短复习、用法变了则指出区别）。这在网页对话里由会话历史白送，在产品中会被 ADR-017 的单句上下文与 ADR-022 的独立调用系统性砍掉。照此实现，产品会在第 200 句时仍然从头讲一遍 `ている`。

**决策**：

1. **「教过什么」不由记忆承担。**它来自 KP 库检索这一确定性事实：用当前句的分词结果匹配已有 KP 的 `lexical_anchors`，取出命中的 KP 注入上下文。**agent 不决定记什么，抽取段已经决定了。**

   注意检索的判据是「KP 存在 + 命中本句」，**不按 `retention` 或任何学习意愿过滤**。用户判为 `reference` 的文化互文，正是最需要在下次遇到时被注入的东西——否则模型会再从头讲一遍典故。

2. **记忆只承载风格与画像**，分两类：
   - **作品笔记**（material scope）：人物关系与称呼变化、作品语域与作者癖、复现的固有名词、该字幕的翻译倾向。天然有界，作品读完不再增长。
   - **学情画像**（user scope）：反复在连体修饰节的 `の` 上栽、听力误判集中在词边界、偏好少讲助词。跨作品带走。

3. **上限由后端强制，不由 prompt 约束。**给 agent 的是**有限槽位**：条数上限 N、单条字数上限 M。写满后 `add` 一律拒绝，必须改用 `replace` 或 `merge`。长期未命中走 LRU 淘汰。不要在 prompt 里写「请你克制」——那不是约束，是希望。

4. **对用户可见、可编辑、可删除。**系统对你的判断，你有权看见。

**为什么不用一份平行的散文记忆**：KP 库已经是结构化、去重、可合并、用户可编辑的记忆。再让 agent 维护一份平行记忆，两者必然互相矛盾，且 agent 那份不可查询、无边界、会漂移。

**结构性不对称，需要记录**：词汇类 KP 有 `lexical_anchors`，再遇由算法免费触发；语法类 KP 没有可匹配的算法锚，只有在下一次解析恰好又抽到它时才会再遇。因此**语法 KP 的再遇率结构性偏低**。缓解手段是为高频语法锚写模式匹配规则，但该项**不在 MVP 内**——MVP 的记忆注入只做词汇锚匹配。

**风险与兜底**：记忆效果可能不佳，甚至无法有效限制。但风险可控，因为**最重要的那一半（讲过没有）由检索承担**。即使笔记完全失效，跨句体验也只退回「不重复讲」这一基线。注意失败模式不只是「没记住」，还有「记住了但因此讲太少」。

## ADR-034　知识点的内部表示：模式语言 + shape 判别式

**状态**：已接受（枚举覆盖率待实测）

**修订**：ADR-005 决策四的锚点书写形式部分

### 以下决策明确不受影响

| ADR | 条目 | 不受影响的理由 |
|-----|------|---------------|
| ADR-005 决策一 | 两层分离 | Lexeme 层完全不动，`lexeme_id` 仍由三元组派生 |
| ADR-005 决策二 | 显式指认 | MVP 内唯一指认来源仍是解析抽取 |
| ADR-005 决策三 | KP 为全局实体 | Occurrence 仍无条件记录、永不去重 |
| ADR-005 决策五 | 主键是形式级 | 同一形式的不同含义共享同一 `kp_id` |
| ADR-005 决策六 | 合并永不原地改写 | `canonical_id` 机制原样保留 |
| ADR-009 全部 | 可校验内容交给算法 | 模型只给语义判断，payload 由算法校验 |
| ADR-017 决策一 | 两段式 | 第一段生成、第二段抽取，不受 anchor 表示形式影响 |
| ADR-017 决策二/三 | 解析是文档 | 小节化、可寻址、可追问，与 anchor 表示正交 |
| ADR-017 决策五 | 抽取由用户触发 | 触发时机不变 |
| ADR-017 决策七 | 持久化分三档 | Analysis / Occurrence 分离持久化不变 |
| ADR-021 全部 | 多值标签 | `anchor_shape` 是序列化格式判别式，标签是语言学分类，二者正交 |

### 主论据

把 KnowledgePoint 的锚点从「模型自由书写的规范串」改为「模型填写的结构化 payload + 由代码确定性派生的自然键」，核心理由是**把不可检测失败转成可检测失败**。

自由串 anchor 的失败是静默的：模型写 `〜ことができる` 还是 `V辞書形 + ことができる`，代码无法判定哪个错了——两个都合规、都可读、都能落库。错误只能靠事后统计漂移率发现，且发现了也无法自动处理。

结构化 payload 的失败大部分是可检测的：模型输出槽位与字面量序列，并给出槽位在原句中的绑定，后端可以拿 sidecar 逐条校验——绑定的 POS 与声明的 category 是否相容、字面量是否按序出现在 surface 中、活用形是否与声明的 form 一致、0 槽位模式的字面量是否恰好等于一个 lexeme。全部是确定性检查。

**本论证与 ADR-009 否决字符偏移、改用子串定位所用的是完全同一条论证**：偏移的典型失败是「整体偏了两位」，仍能对齐、是静默错误；子串的失败是「找不到」，100% 可由代码检测。本次修订把同一条论证从 Span 层推进到 anchor 层。

「输出更稳定」是后果，不是理由。

### 决策

**判别式：`anchor_shape`**

判别标准只有一条：**这个取值是否改变了 payload 的形状。**

shape 只有三个取值，外加一个逃生舱：

| shape | payload 形状 | 例 |
|-------|-------------|---|
| `pattern` | 字面量与槽位的有序序列 | `N₁のない＋N₂`、`なければならない`、`〜に対して` |
| `lexical` | 单一词形字符串 | `向上心`、`気にする` |
| `entity` | 外部实体标签 + 实体类型 | 夏目漱石《こころ》 |
| `opaque` | 自由串（逃生舱） | 无法用 pattern 表达的构式，见下 |

**模式语言 v0**

```json
{
  "shape": "pattern",
  "pattern_grammar_version": "0.1",
  "elements": [
    {"type": "slot", "id": "N1", "category": "N", "form": "none"},
    {"type": "literal", "text": "の"},
    {"type": "literal", "text": "ない"},
    {"type": "slot", "id": "N2", "category": "N", "form": "none"}
  ]
}
```

**category（六项，v0 上限）**：`N` / `V` / `A-i` / `A-na` / `Clause` / `Any`

**form（八项，v0 上限）**：`none` / `base`（辞書形）/ `continuative`（連用）/ `te` / `past` / `negative` / `attributive`（連体）/ `conditional`（ば）

刻意压到这个规模，枚举空间有限，已知的缺口（意向形、使役被动、敬语级别）不在 v0 补，先走 `opaque`，由实测数据决定加哪一个——这正是逃生舱的价值所在。

**模式属 KP，绑定属 Occurrence**

- **`elements`（模式本身）存 KnowledgePoint**——它是可复用的概念；
- **`bindings`（N1 = 向上心、N2 = しまむら）存 Occurrence**——它是一次具体出现。

绑定的每个槽位实例还应指向一个 Span（复用现有值对象）。

**自然键派生**

`anchor_key` 由 `elements` 确定性序列化得到，模型**不书写它**，与 `lexeme_id` 由三元组派生同构。

- 序列化只取 `category + form + literal 文本 + 顺序`，**不取 slot id**（`N1`/`N2` 只是绑定用的局部标签，不参与身份）；
- 派生结果仍写入 `anchor` 字段并保留数据库唯一约束（不变量 11 不变），并发 upsert 行为不变;
- 归一化折叠规则（若将来引入，如 `NP → N`）必须是一张**版本化的映射表**，展示层保留原始 payload，键层用折叠后的值。v0 不引入任何折叠，六个 category 之间无包含关系。

`display_form` 的语义随之改变：默认由渲染器从 payload 生成（`N₁のない＋N₂`），字段本身退化为**可选的人工覆写**。

**逃生舱：`shape = opaque`**

没有逃生舱，模型会在撞墙时扭曲输出，而扭曲输出是静默错误。这与本次修订的主论据直接冲突，因此逃生舱不是妥协，是设计的一部分。

payload 为自由串，书写规则沿用 `prompt-contracts.md` §7.1 的现行临时规范。

必须区分两种来源，落成字段 `opaque_reason`：

| 取值 | 含义 | 用途 |
|-----|------|------|
| `model_chosen` | 模型主动判断无法表达为模式 | 反映 DSL 覆盖缺口，是扩充枚举的第一手依据 |
| `validation_failed` | 模型给了模式但校验不过，被降级 | 反映 prompt 或校验器问题 |

两者不得合并统计。前者告诉你语言里还有什么没覆盖，后者告诉你实现哪里有毛病。

**校验规则清单**

实现时应写成断言，逐条对应一个可测量：

1. 每个 `literal` 的文本按声明顺序出现在该 Occurrence 的 surface 中；
2. 每个槽位绑定是原句中的连续子串，且能定位到 Span；
3. 绑定的 Sudachi POS 与声明的 `category` 相容（维护一张 POS → category 映射表，代码侧）；
4. `form` 可校验时校验，不可校验时记 warning 不阻断（活用形判定并非全部可靠）；
5. **0 槽位模式若其字面量串在 sidecar 中恰好等于一个 lexeme，必须写成 `lexical`**——又一条免费的确定性 lint，写入时执行一次，结果连同 `analyzer_dict_version` 存入 KP 的 `zero_slot_lexeme_check` 字段；
6. `entity` shape 不参与 1–5，其身份不可校验，这是接受的代价（此类 KP 绝大多数会被用户置为 `reference`）；
7. 任一条不通过 → 记入 `ExtractionRun.invalid_patterns`，按策略降级为 `opaque` 或触发重跑；
8. 槽位绑定不得重叠或逆序：同一模式中各槽位在原句中的出现顺序与 `elements` 中的声明顺序一致，跨槽位的 Span 不相交。

**不连续构式：v0 留位，不实现**

`〜ば〜ほど`、`Vても、Vても`、`〜のではないか` 这类扁平序列表达不了。估计有一到两成构式撞上。

- 语法层留 `optional` / `repeat` 标记的位置，v0 不实现，撞上就走 `opaque`；
- **但 `Occurrence` 的单 Span 限制现在就要放开**：不连续构式的实例天生需要多个 Span。`occurrence_spans` 关联表已有 `ordinal`，物理上支持，只是文档写死了「MVP 中每条 Occurrence 恰好一条」。按「不可推迟」的判据（后补代价是全量迁移），schema 与不变量现在就按有序数组写，实现先只用长度 1。

### 后果

1. **免费的填空题**：已知哪些字符是字面量、哪些是槽位实例，配合已有 Span，可直接从原句生成 cloze——挖掉字面量考构式，或挖槽位考搭配。这正面回应了「可测试」这一条，且不需要建 `LearningJ-plan-v5.md` §8 推迟的完整听力题型系统。**这是这套额外结构最直接的回报。**

2. **特化关系可计算**：一个模式是否是另一个的特化，是槽位精化关系（`Any` → `N`、`form: none` → `form: attributive`、字面量增加），代码可判定，不需要存边。相似语法关联有相当一部分在这里免费拿到。

3. **别名表退化**：自由串漂移消失后，Alias 表不再承担吸收模型措辞变体的主要职责，退化为「JLPT 种子串 / 教材写法 → 模式」的映射与外部导入通道。规模从原估计的数千条降至数百条。

4. **需要长期维护一门小语言**：语法定义、校验器、渲染器、POS 映射表、种子数据、版本迁移。§1（免费的 cloze）与可校验性是它挣回成本的地方，但成本是真实的。控制手段：枚举压到六 + 八、不实现 optional/repeat、不引入折叠表、不引入关系边、逃生舱兜底。**先窄后宽，由数据决定往哪个方向长。**

5. 渲染器逻辑必须版本化（与 prompt 同理）：`render_anchor_for_display_v1(kp)`。改变渲染规则需新建函数、不得原地改写，否则历史截图 / 导出的 Anki 卡对不上。

6. Anki 导出的 anchor 渲染：用户可直接用 `display_form` 或从 payload 自行渲染。`render_anchor_for_display()` 函数不只服务 Anki 导出，也用于聚合视图、收件箱等其他展示场景。

7. `pattern_grammar_version` 递增策略：
   - 新增 category / form 枚举项 → 小版本递增（0.1→0.2），历史 KP 不受影响
   - 改变 `anchor_key` 序列化算法 → 大版本递增（0.x→1.0），需批量重算键并**按 `canonical_id` 合并冲突项**（ADR-005 决策六），不是原地覆盖

8. 跨语言扩展（MVP 不涉及）：当前 `pattern_grammar_version` 默认日语（格式 `0.1`）；若支持其他语言，采用 `{lang}_{version}` 格式（如 `ja_0.1` / `zh_0.1`）。

9. 首版即新格式，无历史数据迁移问题。

### 代价与约束

`pattern_grammar_version` 是 KP 上的必填字段——模式语法是可变规范，不记版本则第一次给枚举加项，历史 KP 的键就不再可信。这与全套文档「涉及外部资源或可变规范的记录必带版本戳」的房规一致。

## ADR-035　身份消解：释义不参与身份判定，第二轮条件触发

**状态**：已接受

**修订**：ADR-017 决策六第二段执行路径，新增身份消解轮的触发条件

### 决策一：释义不参与身份判定

原思路中「让 AI 比对已有释义来决定沿用还是新建」应当否决。理由来自文档自身：

ADR-005 决策五已拍板主键是形式级而非义项级，义项差异保留在各条 Occurrence 里。这意味着**释义的不稳定性已经被隔离在身份层之外**了。同一模型连问两次给出不同释义，在现有模型下不是缺陷，是两条 Occurrence，聚合视图并置展示——「差异不但没被磨平，还成为学习内容本身」。

让释义回到「沿用还是新建」的判断里，等于把一个已经关掉的问题重新打开，且打开在最贵的地方。

### 决策二：第二轮改为条件触发

原方案担心的时序问题（抽取前只有一大段解析，无法检索）在模式语言下大幅缓解：模式含字面量部分（`の`、`ない`），可以按**字面量序列**给 KP 建倒排索引，用**原句本身**做候选召回。召回发生在抽取之前，不需要多一轮。

派生出的三分支（`prompt-contracts.md` §5.3 已定义）：

| 情形 | 动作 | 模型调用 |
|-----|------|---------|
| `anchor_key` 已存在 | 直接复用 | **零** |
| 键不存在，但归一化近邻存在 | 问一次「复用还是新建」 | 一次小调用 |
| 键不存在且无近邻 | 直接新建 | **零** |

绝大多数句子的第二轮成本为零。这一点是硬约束：ADR-017 已把「成本模型多了一个乘数」列为代价，A 类又是成本上最危险的人群，一个常驻的第二轮 LLM 调用过不了产品自己设的关。

### 决策三：检索增强的定位随之变化

`prompt-contracts.md` §5.3 现有的「top-k 模糊匹配候选 + 复用其一或新建」保留，但性质变了：从**唯一防线**变成**召回优化**。真正把生成压回闭集的是 DSL 与校验器。`k = 10` 的临时值可保留，其调参重要性下降。

### 后果

- 检索增强仍然必要（冷启动、术语一致性），但不再是可校验性的唯一手段；
- 近邻召回触发率需在 `spike-checklist.md` 实验 2 中测量，并用实验 9 的 token 成本数据折算成 A 类日成本增量，与 `LearningJ-plan-v5.md` §13 的商业判断挂钩。

# 三、已否决

## ADR-002　AI 解析按「一般层 / 实例层」分层

**否决理由**：音变等带来的细小差异使重复率本就不高，强行规范化会磨平相当一部分有价值的学习内容。

该理由导出了 ADR-005 的核心原则「归一锚点，不归一内容」。替代方案见 ADR-017。

## ADR-003　不做整句解析的共享缓存

**状态**：暂缓（非永久否决）

**理由**：整句解析复用率约等于零；BYOK 导致质量参差，劣质内容混入共享池比无共享池更糟；真要做需要官方聚合渠道与审核机制。

**留口**：Occurrence 记录模型、prompt 版本、抽取模型版本、用户是否标记有用。ADR-014 的高亮单条反馈亦为免费的种子数据。
