# ADR-042 开发库重建与正式数据基线

## 决策

**2026-09-11 用户补充决定：当前开发阶段统一采用删除指定开发／测试数据库并按当前 schema 重建，不需要迁移旧数据库。** schema 调整直接更新初始化基线与可复现 fixture，不新增旧版本前滚链、legacy 回填或兼容分支；旧库升级成功不作为当前阶段验收或下一包启动条件。已有迁移及其测试结果是历史实现证据，不要求为本次开发继续维护；本决定本身不执行文件删除。

**2026-09-12 用户决定执行文件删除：**上一段的不维护边界已落实为移除——alembic 迁移链（`env.py`、`alembic.ini`、全部历史 revision）、迁移前备份／`forward_upgrade`、旧库回归样本、对应测试与 `alembic` 依赖均已从仓库删除，git 历史保留为历史事实。开发期唯一建库路径为显式删除重建；全库快照导出与隔离验证保留为 P1 产品能力，其 manifest 的 schema／契约身份读自数据库的开发基线登记表。未来首次真实数据／对外发布前，按 §1.6 以当时的当前 schema 为锚点新建受支持基线的版本化迁移、升级前备份与隔离恢复检查，不恢复本条删除的工具链。

项目仍处于没有实际业务数据投入使用的开发阶段。对于明确指定的开发／测试数据集，契约调整使用显式删除重建并重新灌入可复现 fixture。重建命令须明确目标路径，不需要额外建立复杂的数据集注册或迁移管理平台；普通启动、打开数据库或版本不匹配不自动删除数据，不得借此删除源素材、秘密、导出文件或其他目录内容。

在首次保留真实学习数据或首次对外发布持久化版本之前，必须登记明确的 schema 基线、应用／契约版本和支持的数据库版本范围。从该时点起，受支持数据库的升级必须使用版本化迁移，升级前生成可打开的备份，并执行隔离恢复检查；不能再以“开发期”规避历史数据保护。全库快照导出与恢复继续是 MVP 能力。

无论开发库是否可重建，运行时都必须保护被引用的分析版本、学习事实和用户决定，并保留事务、幂等、版本检查和失败恢复边界。现有迁移、旧库审查和已经发生的实现只作为历史事实保留；它们不要求未来继续为尚未发布的开发 schema 增加完整 legacy 前滚、回填或兼容分支。本 ADR 不删除现有数据库、代码或迁移，也不宣称实现已完成。

## 理由与取舍

在没有实际用户数据的早期阶段，为每次字段和契约试验维护完整旧 schema 的前滚链，会把临时实现约束固化为长期负担，也容易让旧字段继续影响新设计。可复现 fixture 和显式重建足以支持这一阶段的开发验证，同时把不可逆的数据保护边界前移到真实数据首次出现之前。

重建权限只覆盖被明确指定的开发／测试数据集，并不授予后台任务自行清空数据的权限。真实数据出现后，备份、版本化升级和恢复检查成为支持范围的一部分；保护引用和事实的原则也不会因 schema 基线转换而改变。
