## 0. 一句话主张

**较为方便地获取 AI 解析、便于回看地保存产生的大量解析内容、把特定解析提取为可持久化的知识点并使其再遇。**

这三件事目前在日语学习工具链中普遍空白，且对所有目标人群都成立。产品的其余部分（词典、翻译、注音）是准入条件；依存分析 + 可视化是未验证学习效用的市面空缺；预计加入的原生多模态（视频、音频与文本一样都是第一公民）以及各部分的结合有潜力润滑优化学习体验，但不是绝对的差异化来源／技术壁垒。

**v4 补充**：主张中的「获取解析」在 v4 里从「获得一份讲稿」升级为「一次可追问、可修订的互动」。理由见 ADR-028——真正产生价值的常常不是解析本身，而是用户提问之后模型给出的那一段。

## 1. 受众：两个市场 + 一个留存阶段

### A 类：零基础启蒙者（N5 以下）

几乎没有活用、语用等概念，阅读理解能力接近零，极端情况下五十音未完成。不希望纯粹走 JLPT 应试路径，希望以沉浸方式优先建立实际沟通能力。

- AI 解析是**主要学习方式**，而非补充；
- 已知词表及学习数据积累少，几乎冷启动从零开始；（由此推知基于词汇覆盖率的「难度推荐」在这一阶段几乎失去意义）
- 无法验证解析正确性（见 ADR-009）；
- 音视频素材对其价值主要在**动机与多模态线索**，语言学上的可理解度低（见 ADR-008 与第 8 节）。

**约束一**：A 类的实际可达时间晚于 B 类一个发行工程。原因见 ADR-020——A 类恰恰比较可能是装不动本地服务的人群，而本地后端是 ADR-010（本地媒体文件）唯一顺畅的形态。这不改变「两个 shell 都做」的决定，但它是排期上的既定事实。

**约束二（v4 新增）**：A 类是**成本模型上最危险的人群**。稠密使用意味着解析次数正比于阅读句数，而 ADR-028 的会话形态又给每句加了一个可变乘数。因此「一次性完整解析是默认路径、会话是升级项」这条约束（`prompt-contracts.md` §2.4）对 A 类尤其不能松。

### B 类：沉浸社群

已在使用 asbplayer + yomitan + Anki 组合，或 Migaku / LingQ 等付费产品。

- 技术能力强、愿折腾配置、付费意愿低（自建工具链一侧）；
- 互操作是高价值的**准入条件**而非普通加分项；
- AI 解析对其价值在于「沉淀与再遇」这缺失的一环，尤其是母语文化者才能理解的社会／时代背景与梗；
- BYOK 对其是自然的，且与开源定位自洽；
- 把学习数据通过本地 API 或 MCP 暴露出去，成本低、受欢迎；
- 主力社群以英语为母语——这是 ADR-024 的直接依据。

### C 类：高水平语用文化读者

日语水平较高，希望进一步体会文本在母语文化语境中的额外意义。

- 值得分析的句子**他们未必能感知到**——读起来只是不明所以，甚至在不知情下误解；
- 需要的是批注与检索，**不是复习**（梗是一次性的，看懂即完）；
- 解析侧重语用、文化与互文，而非语法。

C 类在人群构成上大量重叠于 B 类的成长后期，因此在**路线图上**优先作为 B 类的留存阶段处理；但这不否认 C 类作为独立需求存在。获客与留存是结果而非设计输入，不作为功能取舍的绝对依据。

**v4 修正**：C 类的核心需求「要批注与检索、不要复习」在 v4 中获得了直接的数据支持——KnowledgePoint 的 `retention` 字段取 `reference` 时，条目建 KP、进聚合视图与检索，但不生成 ReviewItem。这项能力**在 MVP 内就存在**，成本是一个枚举字段。推迟的只是 C 类的**发现机制**（ADR-014），不是 C 类的内容承载。

**排期**：C 类相关的发现机制整体推到很后面，见 ADR-014。

### 明确的非目标

**应试人群不排除，但不为其做不顺路的优化。** 见 ADR-012。

## 2. 交互内核

三类人群的差异不在功能清单，而在**解析的触发方式**。

| | 触发方式 | 频率 | 「主动交互即价值信号」是否成立 |
|---|---|---|---|
| A | pull | 稠密（几乎每句） | **不成立** |
| B | pull | 稀疏（卡住时） | 成立 |
| C | push | 由系统标记 | 不适用 |

**B 类**：右半屏解析视图默认折叠，AI 解析是例外路径。原文档「用户主动付出的一次交互成本就是最干净的价值信号」在此完全成立。

**A 类**：当用户点击了全部内容时，点击不再携带信息。原计划以卡片流入口 + 推荐来补偿，现推迟（ADR-022）。MVP 阶段的替代方案是：A 类在阅读器中按顺序手动逐句解析，并提供**多选 + 批量解析**以降低操作负担。真正防止复习队列失控的机制改为闸门体系（ADR-019 + ADR-031），不再依赖推荐做筛选。

**C 类**：主动触发 pull 之外，可能有必要做被动标记的辅助推送。形态为**可疑句高亮**而非「过滤后直接解析」，见 ADR-014。

### 关于「语法与单词是正确的划分吗」（v2.1 遗留问号）

结论：**它不是学习内容的划分，而是当初为了标识符空间做的划分**（词有 UniDic lemma ID，语法点没有），被误当成了前者。它漏掉了惯用搭配（気にする、腹が立つ）、缩约与音变形（〜ちゃう、〜とく）、语域与敬语级别等。

处理方式：不引入单值 `type` 字段做分区，改为**多值标签**，见 ADR-021。

**v4 补充**：ADR-026 之后这个问题被更彻底地解决了——语法与词汇在 KnowledgePoint 层根本不需要区分，二者的自然键都是同一种东西（形态规范锚点串）。区分只以标签形式存在，用于筛选与展示，不用于身份判定。

## 3. 两个 shell，一套底座

阅读器 shell 与卡片流 shell 共享同一套数据模型、解析引擎与复习逻辑，但入口、交互与 UI 有必要做出差异。

### 素材的统一抽象（v4 新增）

「音视频与文本同为一等公民」这句话在 v3 中一直是意向性的。它的可验证形式是：

> **素材 = 有序 Sentence 序列 + 可选时间戳 + 可选 locator。**

视频、音频、文本的差异全部落在「时间戳有没有」与「locator 指向什么」上。**上层的解析、抽取、复习、聚合不得感知素材类型。**这是一条架构约束，可以写成测试。

### 阅读器 shell（MVP 内）

单位是**一部作品**。左半屏阅读器／播放器，可折叠的右半屏解析视图。A 类同样可以使用它自行阅读并手动控制学习，配合多选批量解析。

> **注（撰写者保留意见，未讨论）**：MVP 接受的素材类型若维持 v3 的四种（视频、音频、PDF、EPUB、纯文本），意味着四种渲染器与四种句子定位锚点，是不小的工程。建议 MVP 收窄到**字幕文件（含挂载视频／音频）+ 纯文本 + EPUB**两种，暂不做 PDF。`Sentence` 的位置字段已按「锚点类型 + 类型特定 payload」的两段式形状设计（`data-model.md` §8.2），故此项收窄不产生后续迁移成本。列入未决事项第 8 条。

### 复习视图（MVP 内，v4 明确）

v3 第 3 节留有一问：既然 MVP 自建 SRS，复习视图是否配套做？

**答：要做，且它是 ADR-023 的试金石。**

复习视图与卡片流 shell 是同构的——都是「一个队列 + 一个组件」，区别只在队列来源（SRS 复习队列 vs 推荐分发队列）与承载组件（复习卡片 vs 解析视图）。因此先做复习视图有双重收益：

1. 自建 SRS 没有复习视图等于没做；
2. **若复习视图能在不修改任何组件的前提下装配出来，ADR-022 推迟卡片流的风险基本清零**；若装配不出来，会在 MVP 阶段而非半年后暴露 ADR-023 没落实。

### 卡片流 shell（推迟）

单位是**一次会话**。今天学 N 句，句子由推荐给出，可能来自不同材料。作品退化为素材来源。

**推迟理由**见 ADR-022。核心是：它背后的推荐算法、知识点密度估计都是欠实验的逻辑，早做即早埋；而它的缺失不致命。

### 术语区分（重要）

「队列」在此前讨论中指多样东西，文档中必须分开：

- **推荐分发队列**：今天学哪几句。属于卡片流 shell，**推迟**。
- **SRS 复习队列**：今天复习哪些卡。属于自建 SRS，**保留在 MVP 内**。
- **待确认收件箱**：异步抽取产出的知识点候选的兜底入口，见第 6 节，**保留在 MVP 内**。注意 v4 起改称「收件箱」而非「队列」，这是有意的——见第 9 节，它不是待办清单。

### 两者互相引用（卡片流实现后）

- 卡片背面可跳转至该句在原作品中的位置（前后各一句、可播放对应音频片段，若有）；
- 阅读器中的任意句子可被标记进卡片流。

## 4. 输入端与持久化

### 接受的素材

- 视频 + 可挂载字幕
- 音频 + 可挂载字幕
- 文本（PDF、EPUB、纯文本等）——MVP 范围见第 3 节注与未决事项第 8 条
- 来自其他平台的数据（Anki、jpdb 等）

### 视频不存副本

**媒体身份 ≠ 媒体存储。** 存储的是 locator（文件句柄或路径）+ 内容 hash + 字幕 + 时间戳，不存视频副本。见 ADR-010。

音频与文本素材单独复制一份保存是可接受的，但不应僵化处理，还应考虑文件大小（可提供给用户复制与否的选择权，以及本次是哪种处理模式的知情权）。

### 随附译文（v4 新增）

双语字幕素材的译文作为 `Sentence.translation` 独立字段保存，并在解析时传入，**但必须明确标注为参考而非标准**。依据是实录中模型自发的判断：字幕组存在意译与行间未对齐，分析应优先从日文本身与上下文出发。不传译文是浪费，无标注地传译文是误导。

### Sidecar

分句与分词结果以 sidecar（messagepack）形式随素材持久化。sidecar **必须携带**：

- 内容 hash
- 分句器版本
- 分词器版本 + **词典版本**

词典版本是 ADR-018 的硬性要求：Lexeme 的自然键建立在 `normalized_form` 之上，而它会随 SudachiDict 更新漂移，不记版本则第一次升级词典就是全量脏数据。

**v4 补充**：sidecar 还是 Span 对齐的依据（`data-model.md` §1）。产生某条 Span 时所用的 sidecar 版本与后续重新分词后的版本不一致时，token 区间需重算，字符区间不变。

内容 hash 的另一个用途是留口：将来 sidecar 可以脱离本机复用（同一文件、他人已分析过的 sidecar 可直接取用）。零成本，现在不做。

## 5. 处理 pipeline 与算法／AI 的分界

### Pipeline

1. **视频 →（音轨提取）→ 音频 →（STT）→ 文本 →（处理）→ 可挂载字幕**
   针对无字幕「生肉」。非最小闭环必要因素，MVP 排除。
2. **异构文本素材 →（处理）→ 统一的可解析文本**
3. **文本 →（算法解析）→ 结构化的（sidecar）辅助学习信息**

### 算法层做什么

分句、分词、注音、活用形识别、词频统计、依存分析。

**v4 补充，且这是一条硬边界**：算法层还负责**Span 的 token 对齐**与**三元组的推导**。抽取模型输出的是字符区间，`normalized_form / POS / reading_form` 一律由后端从 sidecar 取，**绝不由模型给出**。理由是模型会写出看似正确但与 SudachiDict 字段不严格对齐的东西，进而污染别名表。这是 ADR-009 的直接推论，v3 未推到这一步。

依存分析与翻译**先按懒生成、只缓存实现**，不持久化。这是暂定值，作为后续可能的修改点记录在此：若性能数据显示重复生成代价过高，或依存结果被用于推荐算法的前置量经常被使用，则改为持久化。缓存 key 必须带分析器版本与词典版本，理由同上。

**AI 解析不进入预处理逻辑。** 这是原文档的判断，予以保留，并且它正是成本可控的根本原因：成本随用户实际学习的句数增长，而非随材料长度增长。

### 分词与依存的实现

**已确定**：SudachiPy + SudachiDict，A mode（与 UniDic 短单位相当）。理由与代价见 ADR-018。

依存分析若进入 MVP，实质等于 GiNZA 进入 MVP——GiNZA 建立在 SudachiPy 之上，与分词选型天然一致，不引入第二套分词。见 ADR-025。

### 算法与模型的职责边界

可被词典与形态分析器校验的内容（分词、活用形、词典释义）**一律走算法**，模型只负责串讲、语用与文化背景。UI 上区分「查得到的」与「模型说的」。见 ADR-009。

## 6. AI 解析：可交互文档 + 两段式

分层的轴既不是「客观／个性化」，也不是「一般／实例」（后者见 ADR-002，已否决）。实际形态是**生成与抽取两段**（ADR-017），且第一段的产物是一份**可追问、可修订的文档**而非一次性讲稿（ADR-028）。

### 6.1 形态：解析是文档，不是消息

一次解析产生一个 **Analysis**，其正文由若干 **AnalysisSection** 组成，每个小节声明它覆盖原句中的哪些 Span（可为空）。用户可在同一个 Analysis 上追问，追问产生新小节或修订已有小节。

这个结构解决了三件事：

1. **回看不再是长篇罗列。**默认视图不是从上往下读，而是**原句带下划线、点哪里看哪里**；对话记录默认折叠。长篇大论的根源不是长度，是线性。
2. **上下文长度基本不是问题。**任何时刻，重放会话所需的完整状态 = 当前小节集合 + 最近 N 轮往返，中间轮次可安全丢弃（其产出已沉淀进小节）。稳态约 5k 到 15k token。
3. **Occurrence 的内容引用有了稳定锚。**引用 `section_id + revision`，而非指向可变 blob 的字符区间。

**不依赖 tool calling**。BYOK 下模型能力分布不均，多轮工具调用是高风险依赖；而单句解析文档只有一两千 token，不需要文件编辑工具。改写以结构化输出表达（按小节 id 返回新增／修订）。详见 `prompt-contracts.md` §3。

### 6.2 第一段：解析生成

对指定句调用主模型，**在给定规范与标准下自由发挥**。

上下文包含：原句、前后文、随附译文（标注为参考）、用户困惑（可选自由文本）、勾选的解析模块、以及记忆注入（见 6.4）。

**结构契约已撤销。**v3 要求「以标题层级承载结构契约」，v4 否决之——实证数据显示前沿模型在单次长输出内部会把并列小节写成 `#` 与 `##` 混用，这类失败率不低且无法可靠检测，而 v3 把整条抽取链路押在了它上面。

替代方案不是把契约挪到文末（那等于把 JSON 换个位置，仍会反向绑架写作，正是 ADR-017 否决直出 JSON 的同一条理由），而是：**第一段正文完全自由，只要求以一个「本句最值得带走的东西」小节收尾**——实录显示这是模型的自发行为，不需要诱导。一切机器可读的结构由第二段产出。

**连带撤销**：「解析风格档位与抽取契约绑定」这条约束不再必要，风格退化为**模块开关**（可勾选 + 可追加自由文本）。v3 未决事项第 1 条由此基本消解。实录同时证明硬档位是错误方向：一次面向低水平学习者的解析里出现了《こころ》互文——**好的解析本来就跨档位**，用互斥预设去切它会切坏。

**是否同时传入结构化解析信息（分词、活用、依存结果）**：第一段尚未决定，需要实验；但**第二段必须拿到分词结果**，否则 Span 对齐无从做起。两段的输入不必一致。

### 6.3 第二段：结构化抽取

在用户阅读解析的同时，依知识点规范从解析文档中提取结构化信息。

**执行路径有两条**：

- **续轮**（默认快路径）：在第一段的会话基础上新开一轮，同模型执行。优势是同一模型在同一语境里知道自己刚才指的是什么，且去掉了误解用户内容的可能。
- **独立调用**（必须支持）：输入为「解析全文 + 规范 + 候选 KP」，不依赖会话历史。

**第二段的 prompt 必须自足**，续轮只是它的一个快路径。这条约束一写死，抽取规范升级后的批量重抽、以及模型不支持长会话时的降级路径就都免费了。

**关于缓存**：缓存有 TTL，批量重抽必然冷启动，BYOK 下用户 provider 未必支持缓存。**缓存是优化，不是架构前提**；续轮的理由是质量而非成本。

**已知风险**：同会话模型有自洽倾向，可能过抽（把自己写过的全抽出来）并降低复用率（沿用自己的措辞而非库内已有 anchor）。列入 `spike-checklist.md` 实验 1。

**抽取产出的形状**见 `prompt-contracts.md` §5。要点：模型输出 anchor、Span（字符区间）、tags、`salience`、`retention`、以及是否复用某个已有 KP；**不输出三元组**。

### 6.4 记忆注入

实录中模型自发承诺并兑现了跨句记忆——第一次遇到 `ている` 拆得很细，之后简短复习，用法变了则专门指出区别。这在网页对话里是会话历史白送的，在产品中则会被 ADR-017 的「上下文 = 原句 + 前后文」和 ADR-022 的独立单句调用系统性砍掉。照此实现，产品会在第 200 句时仍然从头讲一遍 `ている`。

**修复分两部分，边界必须清楚**：

- **「教过什么」由检索得出，不由模型记住。**用当前句的分词结果匹配已有 KP 的 `lexical_anchors`，加语法锚的模式匹配，取出「用户已学过且出现在本句中」的 KP 列表（带 SRS 状态与首次讲解摘要）注入上下文。这是确定性事实，不会漂移。
- **「这个人怎么学」由记忆承担。**分作品笔记与学情画像两类，见 ADR-029。

由此 KP 库获得了第二个用途：**它不只是复习资产，它是解析的记忆体。**

**连带影响**：为高频语法锚写模式匹配规则，从「可选优化」上升为直接影响解析质量的项——因为它同时喂给记忆注入。这也部分反转了「语法 KP 再遇率结构性偏低」的问题（见第 8 节）。

### 6.5 失败处理

**解析原文与抽取产物分开持久化**（Analysis 与 Occurrence 两个实体）。由此：

- 抽取失败时，只需**重跑抽取**，不必重新生成解析。重新生成既贵又会改变内容（但仍然提供给用户重新生成解析的入口）；重跑抽取便宜且解析原文不变。用户看到的是「知识点提取失败，重试提取」。
- 抽取规范升级后，历史解析可批量重抽。

**v4 改进：失败检测从弱信号变为确定性检测。**撤销标题层级契约后，抽取输出是 JSON，因此以下四项可被代码 100% 判定，触发即重跑：输出非合法 JSON 或不符 schema；`candidates` 为空而正文超过阈值长度；全部 Span 对齐失败；无任何 `salience = primary` 的条目。

弱信号（提示而非自动重跑）：抽出条数与正文长度比例异常、anchor 零复用。

### 6.6 时序与待确认收件箱

抽取是异步的，用户读完即关窗的情况必然大量存在。因此候选不能只在当前解析视图内呈现一次，**必须有待确认收件箱作为兜底**。

**它不是待办清单。**不做未读计数，不做红点，不要求逐条处理，只在用户想补充或反悔时进入。理由见第 9 节：单句可产出十条以上候选，做成待办会让用户永远处于欠债状态。

### 6.7 批量解析

多选 + 批量解析实现为**顺序排队的多次单句调用**，不是一次大调用。理由：一次性把多句塞进同一 prompt 会同时损坏每句的前后文窗口、每句独立的抽取契约、以及 Occurrence 与句子的一一对应。排队式在成本上几乎相同，UI 上是一个带进度的列表，且天然可以边生成边读。可做适度的异步并发优化，提供用户可配置的最大并发数。

**v4 强化：批量解析不进入会话形态。**它产出一次性解析，不开会话。互动课堂与批量精读是两种模式，不合并——让用户对三十句逐个互动是荒谬的。

### 6.8 预取

暂时不做预取，后续可尝试仅在强信号下预取（在某句停留超过阈值时长、或播放中的下一条字幕），设并发上限，不做滚动式全量预取。

## 7. 数据模型

改动成本最高的部分，需要在动工前定死。**字段级契约见 `data-model.md`，本节只记录决策与理由。**

### 7.1 两层，不是一层

v3 的模型把 Lexeme 与 KnowledgePoint 塞进了同一个 ID 空间（ADR-018 原文：「与语法点共用同一套 ID 空间、别名表与合并机制」）。**这是一处建模错误，v4 撤销之**（ADR-026）。

分界依据是一句话：

> **自动解析永远无法确定这个词在这里的意思。**

分词器与词典能回答「这是什么词」，回答不了「这里在讲什么」。后者只有被讲解才存在，而那就是知识点。

| | Lexeme 层 | KnowledgePoint 层 |
|---|---|---|
| 构成方式 | 算法自动生成 | **显式指认** |
| 数量级 | \(10^4\)–\(10^5\) | \(10^2\)–\(10^3\) |
| 身份来源 | 词典（确定性派生 id） | 我们（自签发 id） |
| 别名与合并 | **不需要** | 需要 |
| 承载 | 查词、词形分析、已知状态证据、词频与覆盖率、难度标注 | SRS、Anki 导出、聚合视图、再遇、标签 |

**两层之间是引用关系，不是继承关系。**KP 可以（不必）挂若干 Lexeme 作为 `lexical_anchors`，那是索引，不参与身份判定。

由此，「用户读过的每个词都会创建一条 KnowledgePoint」这种情况被结构性地排除了：阅读推断只产生 KnownEvidence，目标是 Lexeme。

### 7.2 KnowledgePoint 由显式指认构成

**MVP 内唯一的指认来源是解析抽取**（ADR-027）。

这意味着 **BYOK 是核心循环的硬前提**，MVP 没有降级路径。这不必现在解决，但必须明写，否则会在做 onboarding 时才发现。

AI 解析之外的 KP 构造路径列入未决事项第 7 条。已否决的形态：以词典义项选择为内容来源——它把**词典厂商的义项切分变成 KP 的内容边界**，而该切分既不由我们控制、也不面向学习、还会随词典版本漂移。这与「归一锚点不归一内容」的原则冲突。

### 7.3 标识符策略

所有 KnowledgePoint 统一走**自签发代理主键 + 别名映射**，**词汇类与语法类一视同仁**：

- 自然键是**符合形态规范的锚点串**。`〜ちゃう`、`気にする`、`食べる`、`V辞書形 + ことができる` 在这一层是同一种东西，都只是字符串。
- **词汇类 KP 不用三元组做主键。**三元组是 Lexeme 层的自然键，在 KP 层降级为可选的、非主键的 `lexical_anchors` 字段。

这直接解决了 v3 遗留的一个矛盾：若 AI 讲的是「食べちゃった 里的 ちゃう 表示遗憾」，抽取产出的锚点就是 `〜ちゃう`，而不是 `食べる` 的某个变体。**锚点反映的是讲解的重心，不是分词器的切分。**

同一次解析可以从同一个 Span 上产出多条 KP（`食べる` / `〜ちゃう` / `食べちゃう`），彼此不冲突——Occurrence 本就无条件记录、永不去重。需要约束的是「同一次讲解不要把同一件事写成三个抽象层级」，那是形态规范决策表的活（未决事项第 4 条），不是数据模型的活。

### 7.4 实体一览

- **Material**：hash + locator，不含媒体副本
- **Sentence**：文本、位置锚点（类型 + payload）、时间戳、随附译文
- **Sidecar**：分句／分词结果 + 内容 hash + 三个版本戳
- **Span**（值对象）：**被 Occurrence、Annotation、AnalysisSection 与未来的可疑句高亮四方共用**
- **Lexeme**：三元组 + 词典版本，确定性派生 id
- **KnownEvidence**：目标为 Lexeme 的已知状态证据
- **Analysis**：一次解析。模型、prompt 版本、模块集合、用户困惑、注入的记忆 id、检索开关、轮数、状态
- **AnalysisSection**：解析正文的可寻址单元。kind、spans、body_md、revision
- **AnalysisMessage**：用户可见的对话往返
- **KnowledgePoint**：自签发 id、anchor、标签集合、`retention`、`canonical_id`、`lexical_anchors`
- **Alias**：别名串 → KP id
- **Occurrence**：KP × Material × Sentence × Span × `salience` × 内容来源（section 引用）× 抽取模型与版本 × 用户是否标记有用
- **Annotation**：划线与批注，**叶子实体**
- **MaterialNote / LearnerProfileNote**：两类记忆，槽位上限由后端强制
- **ReviewItem / ReviewState**：受每日配额控制

### 7.5 Annotation 是叶子实体

划线 + 批注是比「收藏」更真实的行为原语——收藏是个动词伪装成的名词。词汇收藏可由「只划线到一个词」自然退化而来。

**MVP 内 Annotation 与 KP 之间没有边**（ADR-030）。曾提议「提升 Annotation 为 KP，note 成为首条 Occurrence 内容」，已否决：它让 KP 的内容多了一个**无任何规范约束**的来源，而 KP 是要进 SRS、进导出、进聚合视图的。

**KP 的内容永远来自解析小节，不来自自由文本。**用户划线后若想学它，正确动作是在同一 Span 上发起一次解析。

### 7.6 合并必须可后补，且不可破坏

自签发 ID 意味着「新建条目」不可避免，因此**两条 ID 事后被发现指同一事物**也不可避免。处理方式与 ADR-006 的证据模型同构：**永不原地改写**。

- KnowledgePoint 带 `canonical_id`，合并即把一条指向另一条；
- Occurrence 保持指向它当初指向的 ID，解析时经 canonical 视图归并；
- 合并可撤销。

不这样做的话，第一次误合并就是不可逆的数据损失。

**v4 补充**：两层分离使这套机制的规模从 \(10^5\) 降到 \(10^3\)。Lexeme 不进别名表、不需要 `canonical_id`；词典升级不是合并，而是版本迁移映射。

### 7.7 主键是形式级，不是义项级

语法点的自然键建立在**形态规范串**上，因此同一形式的不同含义（〜てしまう 的「完了」与「遗憾」）共享同一个 ID。

它与 ADR-005 的原则一致：**归一化的对象是锚点，不是内容。** 义项差异保留在各条 Occurrence 的解析片段里，聚合视图把它们并置展示，差异不但没被磨平，还成为学习内容本身。

> **注（撰写者保留意见）**：代价是「再遇」提示会把不同义项并列。若干扰过大，成本最低的缓解是在 Occurrence 上记一个**非主键的义项标记**（由抽取段顺带产出），聚合视图据此分组显示。不影响主键设计，可后加，现在不做。

### 7.8 retention：不是所有知识点都该复习

**[v4 新增]** KP 带 `retention` 字段，取 `srs` / `reference`。`reference` 的条目照样建 KP、照样进聚合视图与检索，但**不生成 ReviewItem**。

典型内容：一次性文化梗、互文典故（如《こころ》「精神的に向上心のないものは馬鹿だ」）、元技能（如「词边界误判」）。

这一个枚举同时解决了 C 类「要批注与检索、不要复习」的需求，成本接近零。

**顺带**：形态规范除了规定「怎么写锚点」，还必须回答**「什么东西不该成为 KP」**。实录中至少有两类锚不住的内容——助词的口语脱落（是现象，不是形式）、词边界误判（是元技能）。它们留在 Analysis 里不抽取即可，这正是 Analysis 独立持久化的意义之一。

### 7.9 已知状态

**存为证据记录，不存可变字段**（ADR-006）。粒度到「Lexeme + 已遇到的活用形集合」（ADR-007）。

**v4 明确：证据的目标是 Lexeme，不是 KnowledgePoint。**

「怎么才算掌握一个词」没有事实性答案，只有口径。因此不去定义它，而让它成为证据之上一个**声明了口径的派生视图**：「见过 n 次未查词」「解析中标为已知」「SRS 中该 Lexeme 关联的 KP 已成熟」是三条不同的证据，合成规则可配置。

### 7.10 红线：两个数不能相加

> **词汇量统计与知识点学习进度是两个数，分别显示，永不相加，永不互相校验。**

前者是 Lexeme 层的覆盖率估计，天然模糊；后者是 KP 层的精确计数。

v3 第 8 节曾担心「聚合视图显示 3 次、再遇计数却是 5 次」的不一致。在两层模型下这不再是 bug，而是**两个有不同标签的量**：「被讲解过 3 次」与「在你读过的材料中出现过 5 次」。用户完全能理解，前提是别把它们印成同一个数字。

## 8. 复习与再现

### 「第二遍就能懂」不是自动的

解析一句是**局部**的，而听力可理解度是**整体**的：一集 300 句，精解 20 句，第二遍仍有 280 句不懂。此外，解析建立的是「读」的理解，而无字幕重看用到的是实时切分连续音流的能力，两者之间没有自动迁移。

**其一，同集内复现优先。** 推荐优先选取在本集内高频（按词根统计）且用户未知的项。——注：此项依赖推荐器，随 ADR-022 一并推迟，但词频统计本身在算法层是现成的，可先用于展示。

**其二，再现有声音则必带。** 若自建 SRS 只复习文字，练的仍然是读。数据模型中包含句级时间戳，抽取数秒音频几乎免费。

**但 TTS 是非必须配置项**，因此非原生带音频的素材，其知识点卡片不一定有音频。卡片模板与 Anki 导出都必须能处理**音频缺失**的情况。

### 复习卡片

- 正面：知识点本身（anchor）+ 例句（Span 高亮）+ 音频（若有）
- 背面：该次 Occurrence 引用的解析小节

**系统排程的复习卡「就事论事」**，只呈现当次实例，不堆历次。历次实例的并置属于聚合视图，不属于复习流。

**ReviewItem 默认每 KP 一条**（ADR-031）。同一 KP 的后续 Occurrence 默认不生成新复习项，而是作为「再遇」进入聚合视图并可选择性更新例句；用户可显式为某条 Occurrence 单独开卡（多义项、或例句本身值得记时）。

这条默认值同时是一层隐性闸门：A 类稠密使用下高频语法点会被反复抽到，若每次都开卡，ADR-019 的每日配额会被同一个 `〜てしまう` 刷屏。

### 聚合视图

用户主动查询某知识点时，展示该知识点下的历次 Occurrence 并置。

**它不是一个新界面**：候选确认时「悬浮展示相近知识点卡片」的浮层就是它的最小形态，主动查询入口只是把同一组件放大成面板。

**聚合的 key 是 KP ID**（经 canonical 视图归并）。同时显示的两个计数必须分别标注来源，见 7.10。

**灵感（未排期）**：可视化展示已学知识点的视图，以各个学习材料为中心节点伸展出知识点图，展示 `canonical_id` 指向等信息，并支持按标签、学习状态、学习状况筛选。

### 语法 KP 的再遇率结构性偏低（v4 新增）

词汇类 KP 有 `lexical_anchors`，再遇可由算法免费触发；**语法类 KP 没有可匹配的算法锚，只有在下一次 AI 解析恰好又抽到它时才会再遇。**

这是模型的结构性事实，不是抽取质量问题——必须写在这里，否则实际使用时一定会被误判。

缓解手段是为高频语法锚写模式匹配规则。它在 v4 中的优先级高于 v3 的判断，因为它同时是记忆注入的输入（见 6.4）。

### 活用覆盖

在词根频次之上，推荐进一步覆盖**同一词根的不同活用形**。完全落在算法层（Lexeme 层），Sudachi 输出中辞書形与活用形均为现成字段。这是 ADR-007 中已知状态粒度要求的直接来源。

TTS 在此有一项原声无法替代的价值：**原声只能给出素材里出现过的句子，TTS 能给出任意词形的读音**。活用覆盖所需的「食べちゃった」在原声素材里未必有对应片段。见 ADR-016。

### 听力

**提议**：先做最退化的形态——同一句先只放音频，用户自评能否听懂（或听写，待定），再展开文本与解析。完整题型系统（出题、判分、反馈）会把产品从辅助器推向课程，待前者被验证有人用之后再议。

TTS 音频**可以**进入这一流程，但记为不同来源与置信度，见 ADR-016。

### Anki 挖矿

支持导出整句卡与知识点卡，带音频、图片，视频切片作为**可选配置项**。

关于 Anki 卡片的导出，不必指定固定格式，只需暴露出字段供用户主动选择、与 Anki 条目对应即可。系统内部的卡片也应允许用户自由配置。

**导出流程刻意保留一点摩擦。** 见 ADR-013。

## 9. 候选与筛选

### 加入学习的默认值（v4 修订）

v3 的「默认全部加入」在 v4 中被修订为**两级候选**：

- **primary**：第一段收尾小节点名的 1 到 3 条 → **默认加入**；
- **secondary**：正文讲过但未被点名的其余条目 → 列出、不默认、一键加入。

**修订理由**：实录显示单句可抽出十条以上候选（仅「汚い、素人相手に変化球使うなんて」一句即有 `汚い` 引申义、`素人`、`N相手に`、`を` 脱落、`普通形 + なんて`、`なんて` 结句、ワ行五段、听感助词消失等）。A 类稠密使用下，待确认收件箱会以每句十几条的速度增长，用户永远处于欠债状态。

**不违反 ADR-019 的精神**：Occurrence 仍无条件全记、永不去重，改变的只是「加入学习」的默认值。显著性判断由抽取段免费给出——模型本来就在做这件事。

### 不做硬性去重

理由不变：即使规范书写完全一致的知识点，在不同语境下也可以表示不同意思、具有不同语感；且即便确属重复，新例句本身也是有价值的资产。

替代方案是**提示而非拦截**：候选项上做超链接式标记，悬浮展示已有的相近知识点卡片（即聚合视图的最小形态）。

真正需要控制的不是候选数量，而是复习队列的增长率——由 ADR-019 的第三层配额与 ADR-031 的每 KP 一条共同解决。

### 推荐（随卡片流一并推迟）

推迟内容包括：选择与推荐算法、知识点密度估计。可用的估算量记录在此备查：

- （陌生）词汇数、句长、依存树形态、是否含未见过的活用形
- 由上述 NLP 可得信息结合用户学习历史／导入状态组合估算的**知识点密度**（此处「知识点」指算法可估的语言点，非最终产出的 KnowledgePoint；不保证准度，仅作大略参考）
- 同集内词根频次与活用覆盖（见第 8 节）

## 10. 互操作

范围：导入既有 Anki / jpdb 已知词表、导出卡片到 Anki、兼容 yomitan 词典格式、其他数据的导入导出、通过本地 API 或 MCP 暴露学习数据。

**时序：部分后置，但证据模型先行。** 见 ADR-011。

冷启动有第二条路：阅读行为本身即产生已知状态证据（划过不查的词、解析中标为已知的词）。因此互操作是「加速冷启动」，而非「让功能可用」的前提。

**关于 lemma_id 的补充判断**：失去 UniDic 語彙素对互操作**没有损失**。Anki 按字符串字段匹配，jpdb 用自己的 vocab id，yomitan 词典按表记加读音索引——整条互操作链路上没有任何一环认 UniDic 語彙素。损失只发生在站内自身的同一性上，已由 ADR-018 与 ADR-026 处理。

**v4 补充**：导入的已知词表落在 **Lexeme 层的 KnownEvidence**，来源标记为 `import_anki` / `import_jpdb`。它**不产生 KnowledgePoint**——这与 ADR-027 一致，导入不是指认。

**高价值目标**：兼容 yomitan 词典格式。即时查词是基础中的基础，yomitan 格式词典丰富，且文件大小一般合适。

> 术语澄清：「难度标注」指依据用户已知词集合对材料／句子给出难度。已知集合为空时所有材料都显示为近乎全生词，标注失去区分度。判断是：阅读行为推断可以逐步填充该集合，故该功能是「初期效果差」而非「不可用」。

> **注**：yomitan 格式词典的**内容**（各家词典）多数不可再分发；VOICEVOX 的角色音源有单独使用规约。开源发行版打包时会撞上，提前记录。

## 11. C 类的发现机制

**整体推到很后面。** 形态为**可疑句高亮**（可配置开关 + 阈值 + 单条反馈），而非「过滤后直接解析」。见 ADR-014。

**注意**：高亮所用的位置表达必须复用 Span 值对象，不另起一套。

## 14. MVP 边界

### 保留

- 阅读器 shell + 句级 AI 解析（含多选批量解析）
- **解析为可交互文档**：小节化、Span 索引、追问追加小节、对话记录持久化
- **算法基础解析**：分句、分词、注音、词典查词、翻译
- 两段式解析（生成 + 抽取）与待确认收件箱
- **两层数据模型**：Lexeme 层（证据、统计）与 KnowledgePoint 层（学习）
- 知识点规范化（形态规范 + 自签发 ID + 别名映射，语法侧从 JLPT 语法表起步做种子）
- Annotation（划线 + 批注 + 检索 + 跳转）
- 记忆注入（KP 检索 + 两类笔记，槽位上限）
- 自建 SRS + 配额 + 每 KP 一条 + 句级音频再现（有则带）
- **复习视图**（见第 3 节）
- 聚合视图（含浮层最小形态）
- Anki 导出
- Python + FastAPI 后端与 sidecar 持久化

### 条件式

- **依存分析 + 可视化**：可视化成本不高（日语文节依存严格右向、非交叉，是一维弧线图而非通用 DAG 布局），但实质门槛在上游——文节切分与 GiNZA 引入。见 ADR-025。

### 排除

- STT pipeline（生肉处理）
- **解析小节的 agent 改写与合并**（`revise` / `merge`）——schema 第一天就有，行为放第二阶段
- 多模态并行支持（但设计中要把音视频当作一等公民，通过第 3 节的统一抽象实现）
- 卡片流 shell、推荐分发队列、知识点密度估计（ADR-022）
- 解析共享后端
- 完整听力题型系统
- C 类发现机制（ADR-014）
- 解析时的联网检索（但 `retrieval_enabled` 字段留位）
- UI i18n（但解析输出语言不在此列，见 ADR-024）

### 不可推迟的数据层事项（改起来最贵）

1. **Lexeme 层与 KnowledgePoint 层分离**（ADR-026）
2. 已知状态存为证据记录，不存字段，**目标为 Lexeme**（ADR-006）
3. 已知状态粒度到 Lexeme + 活用形集合（ADR-007）
4. Occurrence 记录来源元数据（ADR-003 留口）
5. **所有 Lexeme 记录与 sidecar 带词典／分析器版本戳**（ADR-018）
6. KnowledgePoint 的合并机制（`canonical_id`）从第一天就存在
7. Analysis 与 Occurrence 分开持久化
8. **Span 为共享值对象**，Occurrence / Annotation / AnalysisSection / 未来的可疑句高亮共用（ADR-026 之外的独立要求）
9. **AnalysisSection 可寻址**（`section_id` + `revision`），Occurrence 引用 section 而非字符区间（ADR-028）
10. **`salience` 与 `retention` 两个枚举字段**（ADR-031、7.8）
11. **Sentence 的锚点两段式形状**（`anchor_type` + `anchor_payload`）
12. 解析视图与复习组件独立于 shell（ADR-023）
