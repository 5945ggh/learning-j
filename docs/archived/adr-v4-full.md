## ADR-001　受众划分改为「两个市场 + 一个留存阶段」

**状态**：已接受（部分保留）

**背景**：原文档中 A、C 两类按水平划分，B 类按已有工具链与行为划分，三者不在同一平面。

**决策**：路线图上把 C 类作为 B 类的留存阶段处理，不为其设计独立的获客路径；A、B 视为两个独立市场。

**代价与后果**：C 类的功能不因此被砍，只是不单独排期。

**v4 补充**：C 类的内容承载能力（`retention = reference`）已在 MVP 内，推迟的只是发现机制。

## ADR-002　AI 解析按「一般层 / 实例层」分层

**状态**：**已否决**（由 ADR-017 替代）

**否决理由**：

1. 多义——很多知识点有多重含义，一般层的「全局唯一定义」会与之冲突；
2. 音变等带来的细小差异使重复率本就不高，强行规范化会磨平相当一部分有价值的学习内容。

**保留记录的意义**：理由 1（多义）并不构成删除一般层的**独有**理由，它同样作用于 ADR-005 的目录粒度问题；该问题已在第 7.7 节「主键是形式级，不是义项级」处单独回答。理由 2 是真正的决定性理由，且它导出了 ADR-005 的核心原则「归一锚点，不归一内容」。

## ADR-003　不做整句解析的共享缓存

**状态**：暂缓

**决策**：不做。整句解析复用率约等于零；BYOK 导致质量参差，劣质内容混入共享池比无共享池更糟；真要做需要官方聚合渠道与审核机制。

**留口**：Occurrence 记录模型、prompt 版本、抽取模型版本、用户是否标记有用。ADR-014 的高亮单条反馈亦为种子数据。

## ADR-004　KnowledgePoint 为全局实体，出现记为 Occurrence

**状态**：已接受（v4 收窄）

**决策**：KnowledgePoint 为全局实体；每次出现记一条 Occurrence。「再遇」即对 Occurrence 按知识点做的查询。

**v4 收窄**：「全局」指 ID 空间全局，不指「用户的学习范围全局」。用户的学习本身可以有范围——单独学习某部作品中产生的 KP，或主动选择全局范围。范围是查询与筛选条件，不是身份属性，因此不进 KP 实体。

**代价与后果**：知识点的归一成为必需品，导出 ADR-005。Occurrence 无条件记录、永不去重，闸门在别处（ADR-019、ADR-031）。

## ADR-005　知识点形态规范 + 自签发 ID + 别名映射

**状态**：已接受（v4 重述范围）

**背景**：语法点没有通用标识符空间，模型对同一语法点的命名会漂移。

**决策**：

1. 定义**形态规范**，约束知识点名称的书写形式，例如 `〜xxxx`、`V + xxxx`、`V辞書形 + xxxx`；
2. 由抽取段在规范约束下「**选择 + 组合**」出符合要求的字段；
3. 以该规范串为自然键，**自签发 ID**；
4. 维护**别名映射表**，把变体写法收敛到已有 ID；
5. 合并机制见 7.6，永不原地改写。

**v4 重述范围**：本 ADR 只作用于 **KnowledgePoint 层**，但在该层内**词汇类与语法类一视同仁**——词汇类 KP 的自然键同样是锚点串，而非 ADR-018 的三元组。三元组属于 Lexeme 层，不进此机制。见 ADR-026。

**核心原则**：**归一化的对象是锚点，不是内容。** 用户点开一个知识点看到的不是权威定义，而是历次遇到它的实例并置，各自带着当时的解析。

> **注（撰写者保留意见，三点）**：
>
> **其一，形态规范约束的是形状，不是同一性。** 两个都合规的串仍可指同一事物：`V辞書形 + ことができる` / `V + ことができる` / `〜ことができる`。命名漂移由此转化为**抽象层级漂移**，并未消失。缓解手段是规范里附一张**决策表**，使每个点只有一种合规写法。见未决事项第 4 条与 `spike-checklist.md` 实验 2。
>
> **其二，把抽取做成检索增强的「选择」而非开放「生成」。** 抽取前先用模糊匹配从既有 KnowledgePoint 中取 top-k 候选一并交给模型，指令为「复用其中之一，或在都不合适时按规范新建」。这是把开放生成压回接近闭集选择的最便宜手段，也是别名表能自然增长的来源。**v4 已写入 `prompt-contracts.md` §5.3。**
>
> **其三，冷启动。** 第一天别名表为空，而早期数据恰恰最噪。从 JLPT 语法表起步做**种子条目 + 种子别名**，但它不再是封闭目录，只是初始化数据。

**代价与后果**：引入持续的人工维护（合并、归类）。回报是该资产使「语法覆盖率」成为可能——这是 jpdb 结构上做不到的。

## ADR-006　已知状态存为证据记录，而非可变字段

**状态**：已接受（v4 明确目标层）

**决策**：存为证据记录（来源、时间、置信度、词典版本）。已知状态是记录上的派生视图，冲突解决策略可配置。导出到 Anki 时默认只发来源为本站的记录，或至少区分来源并可由用户选择。

**v4 明确**：**证据的目标是 Lexeme，不是 KnowledgePoint。**「怎么才算掌握一个词」没有事实性答案，只有口径；因此不定义它，只让派生视图声明自己用的是哪种口径。

**代价与后果**：查询需经派生层。这是**不可推迟**的工作——现在只写一种来源（阅读推断），成本几乎为零；后补则是全量数据迁移。

## ADR-007　已知状态粒度到 Lexeme + 活用形集合

**状态**：已接受（v4 改写措辞）

**决策**：已知状态记录 Lexeme 及该 Lexeme 下已遇到的活用形集合。

**v4 措辞变更**：v3 写作「词条 + 活用形集合」，其中「词条」在 v3 语境下指三元组代理主键。v4 统一称 Lexeme，语义不变，但明确它属于 Lexeme 层，与 KnowledgePoint 无关。

**代价与后果**：使活用覆盖式推荐成为可能，完全落在算法层。此字段现在加很便宜，后加要重算全部历史。

## ADR-008　为 A 类引入推荐，并新增卡片流入口

**状态**：**部分推迟**（入口与推荐见 ADR-022）

**背景**：「主动交互即价值信号」在 A 类（稠密 pull）上失效。

**决策（推迟部分）**：卡片流 shell、推荐算法、推荐分发队列推迟。防止复习队列失控的职责转由 ADR-019 与 ADR-031 承担。

**否决的方案**：用一个可配置界面加开关同时服务两类（两边都不顺手）——此项仍然否决，卡片流实现时仍应是独立 shell。

## ADR-009　可校验内容交给算法，UI 区分来源

**状态**：已接受（v4 修订第 3 条）

**背景**：幻觉风险在人群间高度不对称，A 类完全无法识别，而他们恰恰把解析当作主要学习方式。

**决策**：

1. 分词、活用形、词典释义走算法与词典资源；模型只负责串讲、语用与文化背景。UI 上明确区分「查得到的」与「模型说的」。
2. 「串讲」不是让模型严格复述算法解析结果，而是在给定规范与标准下自由发挥。
3. **~~自由发挥之上加结构契约：以标题层级约定内容归属~~**——**v4 撤销**，见 ADR-028。替代方案是第一段完全自由、结构由第二段产出。
4. **[v4 新增] 抽取段不得输出可被算法校验的字段。**`normalized_form / POS / reading_form` 三元组一律由后端从 sidecar 推导；模型只给字符区间。理由：模型会写出看似正确但与 SudachiDict 字段不严格对齐的内容，进而污染别名表。这是本 ADR 第 1 条的直接推论，v3 未推到这一步。

**代价与后果**：要求呈现层能混排两类来源的内容。**v3 的「要求解析风格为有限档位」这项代价随第 3 条一并撤销。**

## ADR-010　视频不存副本，存 locator + hash + 句级切片

**状态**：已接受

**决策**：媒体身份与媒体存储分离。存 locator + 内容 hash + 字幕 + 时间戳。挖矿与复习只截取该句对应的数秒音频与可选画面帧。

**代价与后果**：用户删除或移动原文件后需重新定位（hash 可缓解）。另：此条是 ADR-020 中「本地后端」路线的主要理由之一——托管后端无法访问本地媒体路径。

## ADR-014　C 类发现机制：可疑句高亮 + 单条反馈，整体后置

**状态**：提议（且明确后置）

**背景**：C 类未必总能感知哪里有梗，系统 push 是有必要的补充；但全量 AI 解析成本正比于句数，不可行。

**决策（提议）**：

1. 用廉价信号过滤候选句（NER、语域突变、流行语词表、回译语义距离）；
2. 形态为**高亮标记**，而非过滤后直接解析——更省、更安全；
3. 必须配总开关、可调阈值、以及单条「这里没有」反馈。

**关键点**：误报形态因此改变。解析的误报只是多点开一次；高亮的误报是**正文上的持续视觉噪声**，烦人程度高一个量级——这是必须有开关与阈值的原因。同一机制在不同人群上设不同阈值（C 类容忍度高，A 类宁可漏不可错）。

**副产品**：单条反馈是免费的种子数据，见 ADR-003 留口。

**v4 约束**：高亮的位置表达必须复用 Span 值对象，不另起一套。

**排期**：整体推到很后面，不在 MVP。

## ADR-016　TTS 与原声是语体差异，不是质量差异

**状态**：已接受

**背景**：v2.1 的理由是「TTS 音高重音常错、语速匀整」，据此禁止 TTS 进入听力自评流程。该理由**事实层面不成立**——本地可部署级别的 TTS（如 VOICEVOX）质量已普遍不错，速度、语气可调，定制方便；第三方 API 更强。

**决策**：

1. 撤销「TTS 不进入听力自评流程」的禁令。
2. TTS 与原声的真实差异是**语体**而非质量：合成语音是朗读体，发音完整、不吞音、不重叠、无环境声、语速匀整；而听力的真正难点在连读、缩约、抢话与噪声，调快朗读语速并不产生这些现象。
3. 该差异由**证据模型**表达而非由禁令表达：听懂 TTS 与听懂原声记为不同来源、不同置信度（`listening_tts` / `listening_native`），用户自己能在统计里看到区别。
4. **撤销「校验 TTS 音高重音」的提议**——难做且无明确收益，属过度设计。
5. TTS 是**非必须配置项**。因此非原生带音频的素材，其知识点卡片不一定有音频；卡片模板与导出必须处理缺失情况。

**新增的正面价值**：原声只能给出素材里出现过的句子，**TTS 能给出任意词形的读音**。活用覆盖推荐所需的词形在原声素材中未必存在，TTS 是唯一来源。

**具体选型**：待调查，VOICEVOX 仅为举例。注意其角色音源有单独使用规约，开源发行版打包时需处理。

## ADR-017　AI 解析为两段式：自由生成 + 结构化抽取

**状态**：已接受（替代 ADR-002；v4 修订代价条目）

**决策**：

- **第一段（生成）**：主模型在给定规范与标准下自由发挥。上下文为原句 + 前后文 + 译文 + 用户困惑 + 模块开关 + 记忆注入。
- **第二段（抽取）**：依知识点规范抽取结构化信息，经规范层映射为 KnowledgePoint。执行路径见 ADR-028 与 `prompt-contracts.md` §5.4。

**代价与后果**：

1. 抽取成为解析到知识点的唯一通道，因此规范层的质量直接决定沉淀质量；
2. 抽取异步，需要待确认收件箱兜底；
3. Analysis 与 Occurrence 必须分开持久化，以支持「重跑抽取」与「批量重抽」；
4. **~~风格档位与抽取契约绑定，风格不能是自由文本~~**——**v4 撤销**，见 ADR-028。

**备选方案**：要求模型直接输出 JSON（否决——很可能损害生成质量并使解析变得死板）；一般层 / 实例层（ADR-002，已否决）。

> **v4 注**：把结构契约挪到输出末尾的哨兵块，作为**硬性的可提取范围上界**，等同于把 JSON 换个位置，会以同样的方式反向绑架写作，故同样否决。哨兵块作为**软性显著性推荐**则是另一回事，且已被 ADR-028 的续轮方案取代。

## ADR-018　分词选型 SudachiPy + SudachiDict；三元组为 Lexeme 自然键

**状态**：已接受（v4 删除 ID 空间共用条款）

**背景**：对比 MeCab/fugashi + UniDic 与 SudachiPy + SudachiDict。

**决策依据（一异一同）**：

- **异**：词典体积。UniDic 2025.12 轻量包约 664 MB，完整包约 2.8 GB；SudachiDict Small wheel 约 41.8 MB，Core 约 72.3 MB。
- **同**：解析结果等价程度高。表层形、辞書形、規範形、品詞、活用型、活用形均有直接对应；A mode 官方定义为与 UniDic 短单位相当。

**主要损失**：UniDic 語彙素与 `lemma_id` 无严格对应物；多层读音字段不如 UniDic 丰富。

**替代方案**：以 `normalized_form + POS + reading_form` 三元组为 **Lexeme 的自然键**。

**v4 删除**：v3 原文「自签发代理主键；**与语法点共用同一套 ID 空间、别名表与合并机制**」——后半句已删除。三元组属于 Lexeme 层，其 id 是确定性派生而非自签发，不进别名表，不需要 `canonical_id`。理由见 ADR-026。

**硬性要求**：

1. **所有 Lexeme 记录与 sidecar 必须带词典版本号**。`normalized_form` 会随 SudachiDict 更新漂移；换词典时按版本做迁移映射，不假装 key 稳定。
2. **不使用 Sudachi 内部 word id 作持久锚点**——它随词典构建变动。

**代价与后果**：同形同音同词性的异义词无法由自然键区分。评估认为碰撞面小于直觉。互操作侧无损失，见第 10 节。**v4：该碰撞的影响进一步缩小——它只影响 Lexeme 层的统计口径，不影响 KnowledgePoint 的身份。**

## ADR-019　三层闸门：Occurrence / KnowledgePoint / ReviewItem

**状态**：已接受（补充见 ADR-031）

**背景**：担忧的真实对象不是候选列表太长，而是**复习队列的增长率**。A 类稠密使用下，每天数十句 × 每句若干知识点，SRS 会在一周内不可用。但据此砍候选或硬性去重是错误的应对——新例句本身有价值，而 Occurrence 本就永久保存。

**决策**：闸门放在第三层，前两层无条件放行。

| 层 | 策略 |
|---|---|
| Occurrence | 无条件记录，**永不去重** |
| KnowledgePoint 关联 | 无条件建立，「再遇」靠它 |
| ReviewItem | **受每日配额控制**，加入学习 ≠ 立刻进入复习队列 |

**代价与后果**：第三层即 Anki 的 new cards/day，机制成熟、用户能理解、可调。

**v4**：实录数据显示单句候选可达十条以上，仅靠第三层配额不足以让待确认收件箱保持可用，故补充两条机制，见 ADR-031。本 ADR 的三层结构不变。

## ADR-020　后端为 Python + FastAPI；分发方式待定

**状态**：已接受（分发方式待定）

**决策**：

- 基础算法解析在 Python + FastAPI 后端处理（SudachiPy、GiNZA 均在此生态）；
- 分句、分词结果作为 sidecar（messagepack）随素材持久化；
- 翻译与依存分析懒加载，运行在前后端均可；
- **LLM API 调用放在 Python 后端**——除生态理由外，抽取段本就在后端，两段同侧使 prompt 版本、模型标识等元数据只有一个记录点。**v4：会话状态管理与记忆槽位校验同理，也在后端。**

**待定：分发方式。**

- **本地后端**：BYOK 密钥不出本机，与开源定位自洽，且是 ADR-010 唯一顺畅的形态。代价是要求用户装 Python 环境，或由项目出打包发行版（Tauri + sidecar，体积数百 MB 起）。
- **托管后端**：安装成本为零，但需代持用户 API key，且本地视频文件路径访问走不通。

**后果**：B 类可以直接跑裸 FastAPI，A 类必须等打包发行版。**A 类的实际可达时间比 B 类晚一个发行工程。**

> **注（v4 新增，待处理）**：本地后端形态下 BYOK 密钥的存储位置与是否加密尚未规定。属于第一天就该定的小事，不要漏。

## ADR-021　知识点用多值标签，不用单值 type 字段

**状态**：已接受

**背景**：曾提议 KnowledgePoint 带 `type` 字段（lexeme / grammar / collocation / variant / register）做锚点路由与筛选。反对意见：不存在不杂不漏的划分，也没有研究支撑；单值分区字段等于用数据结构假装有一个语言学结论。

**决策**：不加 `type`，改加**多值标签集合**。

**理由**：

1. **锚点路由**的需求已消解——**v4 中更彻底**：ADR-026 之后，词汇类与语法类 KP 的自然键是同一种东西（锚点串），根本不存在按类型分派锚点策略的需要。
2. **筛选与展示**的需求不会消失：「这次复习只过语法」「聚合视图里只看惯用搭配」「这本书里我没见过的语法点有几个」——最后一条正是明确想超过 jpdb 的那一项。

而需求 2 要的是**标签而非类型**：多值、可为空、可重叠、可后加、错了不丢数据。

**MVP 范围**：只需保证「语法」这一个标签能被可靠打上。其余标签随需要再长。

**顺带**：标签也是第 9 节「以后不学同类型的这个」中「同类型」的实现依据。

**注意区分**：标签与 `retention` 是两回事。标签描述「这是什么」，`retention` 决定「要不要排程复习」。二者正交，不可合并。

## ADR-022　推迟卡片流 shell、推荐算法与推荐分发队列

**状态**：已接受

**理由**：

1. **缺失不致命**。阅读器页面本身即可支撑自主学习；提供**多选 + 批量解析**可进一步弱化影响。
2. **背后是一大堆欠实验的独有逻辑**：选择与推荐算法、知识点密度估计。推迟节省的不只是前端工作量，更是后端逻辑，而这些逻辑目前缺乏实验支撑，早做即早埋。

**术语约束**：「推荐分发队列」推迟；「SRS 复习队列」与「待确认收件箱」保留在 MVP 内。文档中必须用三个不同的词。

**批量解析的实现约束**：多选批量必须实现为**顺序排队的多次单句调用**，不是一次大调用。**v4 补充：批量解析产出一次性解析，不进入会话形态。**

**代价与后果**：A 类在 MVP 阶段的体验弱于设计目标。可接受，因为防止复习队列失控的职责已由 ADR-019 与 ADR-031 独立承担。

## ADR-025　依存分析进 MVP 实质等于 GiNZA 进 MVP

**状态**：提议（条件式，**尚未拍板**）

**背景**：曾判断依存可视化成本高。该判断被推翻——日语文节依存**严格右向、非交叉**，因此布局不是通用 DAG 布线问题，而是一维序列上的弧线图。可视化确实便宜。

**但真正的成本在上游两件事**：

1. **文节切分**。Sudachi 给的是短单位，不给文节。要么自写文节合并规则，要么引入 GiNZA——它建立在 SudachiPy 之上，与 ADR-018 的选型天然一致。代价是模型包体积（ja_ginza 数十 MB 起）。
2. **长句在窄屏上的可读性**。二三十个文节的句子弧线图很快不可读，需要折行或聚焦模式。这是真正会反复调的地方。

**决策（提议）**：依存分析是否进 MVP，按「GiNZA 是否进 MVP」的口径评估，而不是按「画图难不难」评估。

> **注（撰写者保留意见）**：按第 0 节自己的承认——依存分析的学习效用未经验证——加上本 ADR 列出的两项真实成本，我倾向于建议直接将本 ADR 状态改为**暂缓**、排除出 MVP。理由完全来自文档自身已写下的论证，不需要新信息。此项未讨论，列入未决事项第 9 条。

## ADR-026　Lexeme 层与 KnowledgePoint 层分离

**状态**：已接受

**背景**：v3 的 ADR-018 把词汇的三元组代理主键与语法点的自签发 ID 合并为同一个 ID 空间，共用别名表与合并机制。这导致一个荒谬推论：阅读推断产生的已知状态证据指向三元组代理主键，而后者是 KnowledgePoint，于是**用户读过的每个词都会创建一条知识点**，一部小说一万条量级。

**决策依据**：

> **自动解析永远无法确定这个词在这里的意思。**

分词器与词典能回答「这是什么词」（含全部候选释义），回答不了「这里在讲什么」。后者只有被讲解才存在。因此二者不是同一种实体，不该共用 ID 空间。

**决策**：分为两层。

- **Lexeme 层**：算法构成。自然键为三元组 + 词典版本，id 为**确定性派生**而非自签发。**不进别名表、不需要 `canonical_id`、不需要合并机制。**承载查词、词形分析、已知状态证据、词频与覆盖率、难度标注。
- **KnowledgePoint 层**：显式指认构成。自签发 id，自然键为形态规范锚点串（词汇类与语法类一视同仁）。承载 SRS、导出、聚合视图、再遇、标签。

两层之间是**引用关系**：KP 可挂 `lexical_anchors`（可空、可多），**仅作索引，不参与身份判定**。

**代价与后果**：

1. 别名与合并机制的规模从 \(10^5\) 降到 \(10^3\)，人工维护量大幅下降；
2. 词典升级对 Lexeme 层是**版本迁移映射**，不是合并，二者不再混为一谈；
3. **词汇量统计与知识点学习进度成为两个数**，必须分别显示、永不相加（7.10）；
4. ADR-018 的三元组碰撞问题影响面缩小——它只影响 Lexeme 层的统计口径，不影响 KP 身份；
5. 导入的已知词表不再产生 KnowledgePoint。

**受影响的 ADR**：ADR-005（范围收回 KP 层但扩展到词汇类）、ADR-006（目标明确为 Lexeme）、ADR-007（措辞改为 Lexeme）、ADR-018（删除 ID 空间共用条款）、ADR-021（锚点路由需求彻底消解）。

## ADR-027　KnowledgePoint 由显式指认构成

**状态**：已接受

**背景**：ADR-026 分层之后，需要一条判据说明什么才配成为 KnowledgePoint。

**决策**：

> **一条 KP 的存在，前提是有人指着句子里的某处说「这里有个东西值得你学，它是这个意思」。**

被排除的是**被动的、自动的创建**：读过不创建，查词不创建，导入词表不创建。

**MVP 内唯一的指认来源是解析抽取。**

**代价与后果**：

1. **BYOK 是核心循环的硬前提**，MVP 没有不依赖 LLM 的 KP 生成通道。需在 onboarding 正面处理，列入未决事项第 11 条。
2. 用户的即时查词、词形分析、划线批注均不产生 KP，只产生 KnownEvidence 或 Annotation。

**已否决的第二来源**：以词典义项选择为内容来源（「挖矿型 KP」）。否决理由：它把**词典厂商的义项切分变成 KP 的内容边界**——该切分不由我们控制、不面向学习、随词典版本漂移。这与「归一锚点不归一内容」冲突，也与 ADR-009「可校验的走算法」冲突（「这里是哪个义项」不是查得到的，是判断）。

**留待讨论**：AI 解析之外的 KP 构造路径，见未决事项第 7 条。实质能力需求是「用户在 Span 上发起一次显式指认」，内容来源待定。

## ADR-028　解析为可交互文档；撤销标题层级契约

**状态**：已接受

**背景（两条独立的驱动）**：

1. **标题层级契约不成立。**实证数据（`网页对话版本的例句解析实例.md`）显示，前沿模型在高 thinking effort 下的单次长输出内部，会把并列小节写成 `#` 与 `##` 混用。这类失败率不低、无法可靠检测，而 v3 把整条抽取链路押在了它上面。
2. **一次性讲稿接不住最有价值的内容。**实录中信息密度最高的一段（`よっと` / 词边界误判）完全源于用户主动说「我听成了よ！」。产品若只提供单向讲稿，这类信息结构上无处可去。

**决策**：

1. **第一段正文不受任何机器契约约束**，仅要求以一个「本句最值得带走的东西」小节收尾（实录显示这是模型自发行为）。机器可读的结构全部由第二段产出。
2. **解析是文档，不是消息。**Analysis 的正文由若干可寻址的 AnalysisSection 组成，每个小节声明覆盖的 Span（可空）。
3. **用户可在同一 Analysis 上追问**，产生新小节（MVP）或修订／合并已有小节（第二阶段）。
4. **不依赖 tool calling。**改写以结构化输出表达（按 section id 返回操作）。BYOK 下多轮工具调用是高风险依赖，而一两千 token 的文档不需要文件编辑工具。
5. **持久化分三档**：解析文档持久化；用户可见的对话往返持久化（用户的提问本身是学情信号）；agent 内部轨迹不持久化。
6. **第二段的默认执行路径是同模型续轮**，但其 prompt 必须自足，独立调用必须支持。

**连带撤销**：

- ADR-009 第 3 条（标题层级结构契约）；
- ADR-017 代价条目 4（风格档位与抽取契约绑定）。风格由此退化为**模块开关**，v3 未决事项第 1 条基本消解。
- **把契约挪到文末哨兵块作为硬性提取范围上界**同样否决——那等于把 JSON 换个位置，会以同样方式反向绑架写作。

**代价与后果**：

1. **成本模型多了一个乘数。**因此「一次性完整解析是默认路径、会话是升级项」成为硬约束，且**批量解析不进入会话形态**。绝大多数 Analysis 的 `turn_count` 为 1，这是设计意图而非退化。
2. **Occurrence 的内容引用必须改为 `section_id + revision`**，不能是指向可变 blob 的字符区间。
3. AnalysisSection 的旧版本与被合并小节**永不删除**，否则已有 Occurrence 引用会悬空。
4. 需要新的回看视图：默认不是线性长文，而是**原句带下划线、点哪里看哪里**，对话记录折叠。
5. 上下文长度可控：重放所需状态 = 当前小节集合 + 最近 N 轮往返，中间轮次可安全丢弃。

## ADR-029　记忆分为作品笔记与学情画像，槽位上限由后端强制

**状态**：已接受

**背景**：实录中模型承诺并兑现了跨句记忆（第一次拆细、之后简短复习、用法变了则指出区别）。这在网页对话里由会话历史白送，在产品中会被 ADR-017 与 ADR-022 系统性砍掉。

**决策**：

1. **「教过什么」不由记忆承担。**它来自 KP 库检索这一确定性事实：用当前句的分词结果匹配 `lexical_anchors`，加语法锚模式匹配，取出已学 KP 注入上下文。**agent 不决定记什么，抽取段已经决定了。**
2. **记忆只承载风格与画像**，分两类：
   - **作品笔记**（material scope）：人物关系与称呼变化、作品语域与作者癖、复现的固有名词、该字幕的翻译倾向。天然有界，作品读完不再增长。
   - **学情画像**（user scope）：反复在连体修饰节的 `の` 上栽、听力误判集中在词边界、偏好少讲助词。跨作品带走。
3. **上限由后端强制，不由 prompt 约束。**给 agent 的是**有限槽位**：条数上限 N、单条字数上限 M。写满后 `add` 一律拒绝，必须改用 `replace` 或 `merge`。长期未命中走 LRU 淘汰。
4. **对用户可见、可编辑、可删除。**系统对你的判断，你有权看见。

**为什么不用一份平行的散文记忆**：KP 库已经是结构化、去重、可合并、用户可编辑的记忆。再让 agent 维护一份平行记忆，两者必然互相矛盾，且 agent 那份不可查询、无边界、会漂移。

**风险与兜底**：记忆效果可能不佳，甚至无法有效限制。但风险可控，因为**最重要的那一半（讲过没有）由检索承担**。即使笔记完全失效，跨句体验也只退回「不重复讲」这一基线。效果可测，见 `spike-checklist.md` 实验 3——注意失败模式不只是「没记住」，还有「记住了但因此讲太少」。

## ADR-030　Annotation 为叶子实体，与 KnowledgePoint 无边

**状态**：已接受

**背景**：曾把「词汇收藏」列为一项能力。判断是它属于伪需求——收藏是个动词伪装成的名词，真实的行为原语是**划线 + 批注 + 可检索 + 可跳转**，词汇收藏由「只划线到一个词」自然退化而来。

**决策**：Annotation 与 KnowledgePoint 之间**没有边**。

- Annotation 不进 SRS、不进别名表、不需要合并、不需要锚点规范；
- 与 Occurrence 共用同一个 Span 值对象；
- 能力边界仅为：列表检索、筛选、跳回原文。

**已否决的方案**：「提升 Annotation 为 KP，`note` 成为首条 Occurrence 的内容」。否决理由：它让 KP 的内容多了一个**无任何规范约束**的自由文本来源，而 KP 要进 SRS、进导出、进聚合视图。**KP 的内容永远来自解析小节，不来自自由文本。**

**代价与后果**：用户划线后若想学它，需在同一 Span 上发起一次解析，存在少量重复劳动。可接受，收益是 KP 的内容来源保持受控。将来若确需关联，加一个弱引用字段即可，不影响现有 schema。

**三者分工**（这正好回答了「解析形式好、但不易整理与复习」这一原始痛点）：

> **整理靠 Annotation，复习靠 KnowledgePoint，回看靠 Analysis。三者不必互相兼并。**

## ADR-031　候选显著性两级；ReviewItem 默认每 KP 一条

**状态**：已接受（补充 ADR-019）

**背景**：实录显示单句可抽出十条以上候选。v3 的「默认全部加入」在 A 类稠密使用下会让待确认收件箱以每句十几条的速度增长；而 ADR-019 的第三层配额只管住了 ReviewItem，管不住收件箱。

**决策一：候选分两级。**

| 级别 | 判定 | 默认行为 |
|---|---|---|
| `primary` | 第一段收尾小节点名的 1 到 3 条 | **默认加入学习** |
| `secondary` | 正文讲过但未被点名 | 列出、不默认、一键加入 |

显著性由抽取段免费给出——模型本来就在做「最值得带走」的判断。

**不违反 ADR-019**：Occurrence 仍无条件全记、永不去重，改变的只是「加入学习」的默认值。

**决策二：待确认收件箱不是待办清单。**不做未读计数，不做红点，不要求逐条处理，只在用户想补充或反悔时进入。**这一条必须写进 UI 规格**，否则实现会默认给它做红点，然后产品每天欠债几十条。

**决策三：ReviewItem 默认每 KP 一条。**

同一 KP 的后续 Occurrence 默认不生成新复习项，而是作为「再遇」进入聚合视图并可选择性更新例句。用户可显式为某条 Occurrence 单独开卡（多义项、或例句本身值得记）。

**理由**：`retention = reference` 之外，这是第二层隐性闸门。A 类稠密使用下高频语法点会被反复抽到，若每次都开卡，每日配额会被同一个 `〜てしまう` 刷屏。

**代价与后果**：`primary` 判定质量直接决定用户体验，需要实验校准（`spike-checklist.md` 实验 7）。若 `primary` 经常为 0，问题在第一段的收尾小节而非第二段。
